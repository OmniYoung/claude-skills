# SB(화면설계 스토리보드) 생성 — HTML 목업 소스

컨펌된 HTML 화면 목업으로부터 개발자용 화면설계 스토리보드(SB, PPTX)를 만든다. 사용자가 HTML 목업 경로를 주지 않았으면 먼저 요청한다.

> 전제: 화면 기획은 **① HTML 목업 → ② 이해관계자 컨펌 → ③ SB(PPTX)** 순서로 진행한다. 이 스킬은 **목업이 이미 컨펌된 뒤**에 쓴다 — 목업 자체가 아직 안 굳었으면 먼저 HTML을 다듬고 컨펌부터 받을 것.
>
> 목표는 "개발자가 이 SB만 보고 목업을 열어보지 않아도 개발 가능한 수준"이다. 스크린샷에만 있고 텍스트로는 없는 문구(툴팁·토스트·안내문 등)는 반드시 해당 항목 설명에 그대로 인용해서 옮겨 적을 것.

## 준비물

1. **컨펌된 HTML 목업** — 인터랙션(필터·정렬·인라인편집·툴팁·토스트 등)이 전부 실제로 동작해야 함.
2. **재사용 모듈**: `pptx_sb/sb_helpers.py` — 이 스킬 패키지에 함께 포함돼 있어 **별도 설치가 필요 없다**. v1.6 하우스 스타일(파란 헤더 배지, 요약 박스, 번호 지시선, 컬럼 스펙 그리드, 인터랙션 상태 그리드, 표지, 버전 관리 표)이 전부 함수로 있다. 이 SKILL.md를 읽은 실제 경로 기준으로 같은 폴더의 `pptx_sb/sb_helpers.py` 를 찾는다 (설치 위치는 사람마다 다르므로 **사용자에게 경로를 묻지 않는다**). **작업을 시작할 때 이 모듈을 `projects/{프로젝트}/sb_helpers.py` 로 복사한 뒤 그 사본을 import 한다** — 스킬 폴더의 원본을 직접 참조하지 않는다. 플러그인은 계속 갱신되므로, 과거에 승인된 SB 를 다시 빌드했을 때 결과가 달라지면 안 되기 때문이다. 플러그인을 제거해도 기존 빌드 스크립트가 살아있다. 이미 사본이 있으면 덮어쓰지 말고 그대로 쓴다. 사본이든 원본이든 **모듈 자체는 수정하지 말고** import 해서 콘텐츠만 채운다.
3. **파이썬 의존성**: `python-pptx`, `Pillow`, `playwright`(+ `playwright install chromium`)가 사용자 환경에 없으면 설치를 안내한다.
4. **Windows + PowerPoint** — 렌더 검증(PNG 내보내기)과 안전한 파일 닫기(`close_if_open`)가 PowerPoint COM 자동화로 동작한다. 없으면 이 두 기능만 빠지고 PPTX 생성 자체는 가능하다.
5. 원 요구사항 문서(있으면) — SB 완성 후 반드시 원본 요구사항과 항목 단위로 대조한다. 부가 아이디어·수정 요청이 쌓여도 원본 요구사항 커버리지가 항상 최우선 기준이며, 업그레이드는 되어도 누락은 안 된다.
6. **작업 위치는 반드시 사용자 프로젝트 폴더 아래 `sb_build/`**(예: `projects/{프로젝트명}/sb_build/`) — 세션 임시 폴더에 만들면 세션 종료 시 사라져서 다음에 그 프로젝트 SB를 못 고친다. 폴더 구성 권장안:
   - `capture_new_mockup.py` — 목업 섹션/카드 전체 스크린샷 캡처
   - `capture_interaction_states.py` — hover/click/dblclick 등 인터랙션 상태 캡처
   - `build_sb.py` — sb_helpers를 import해서 실제 PPTX를 조립하는 빌드 스크립트
   - `assets/` — 캡처된 원본 PNG
7. **버전 관리 페이지는 모든 SB에 고정으로 넣는다** — 표지 바로 다음 슬라이드로 `sb_helpers.build_version_slide`를 쓴다. 새로 만드는 SB든 기존 SB를 갱신하는 것이든 예외 없이 넣는다.

## 실행 순서

### 0. SB 만들기 전: 확인 질문 · 목업 점검
- **사용자가 정할 수 있는 건 SB 만들기 전에 묻는다.** 확인할 항목을 (1) 동작 정책(저장 방식 · 판정 기준 · 노출 조건 · 문구 · 꺼짐/켜짐 상태 등, 기술 용어가 섞여도 "어떻게 동작해야 하나"면 정책)과 (2) 데이터 · 시스템 사실(필드가 있는지, 연동이 되는지, 현행 값이 뭔지)로 가른다. (1)은 AskUserQuestion으로 먼저 받아 반영하고, (2)만 다른 팀 확인으로 남긴다. 다른 팀 확인으로 넘긴 뒤 "그냥 나한테 물어보지"가 나오면 실패다.
- **영역마다 정상 1케이스가 아니라 끝 경우까지 목업에서 띄워 본다.** 없을 때(0건: 영역 숨김인지, 빈 상자 · 빈 줄이 남지 않는지) · 적을 때(1~2건: 칸이 비어 보이지 않는지, 넘김 · 더 보기가 안 나오는지) · 너무 많을 때(최대 개수, 넘치면 「외 N」 · 더 보기, 고정 영역이 화면 밖으로 밀리지 않는지) · 긴 텍스트(상품명 · 업체명 등 말줄임, 마우스를 올리면 전체). 목업에 그 상태를 보여주는 케이스가 없으면 케이스를 만든다. SB에는 각 경우의 규칙을 한 줄씩 적는다.
- **현행에 이미 있는 동작 · 디자인은 새로 만들지 않고 현행 것을 쓴다.** 담기 후 반응(현행 담기 팝업), 호버 스타일(현행 상품 카드처럼 글자색), 카드 모양, 확인창 등. 목업에 현행에 없는 반응(토스트, 담긴 뒤 버튼 색 변화 등)이 들어가 있으면 SB 전에 걷어낸다. 새 인터랙션을 넣을 땐 현행 사이트의 같은 종류 요소가 어떻게 하는지 먼저 본다.

### 1. 목업에서 스크린샷 확보 (Playwright)
- 섹션/카드 전체 스크린샷(컬럼 스펙 슬라이드용) — 카드 요소의 `bounding_box()` + 8px pad로 크롭.
- 컬럼 헤더 각각의 `bounding_box()`도 같이 뽑아서 JSON으로 저장해두면 `build_column_slide`의 `boxes_px_rel`을 손으로 재지 않아도 됨.
- 인터랙션 상태는 실제로 hover/click/dblclick을 실행시켜서 캡처 (하드코딩된 상태 이미지를 손으로 합성하지 말 것):
  - 호버 툴팁류: hover 후 `wait_for_timeout(150)` 뒤 캡처
  - 편집 모드: dblclick 후 캡처
  - 저장 완료(애니메이션 있는 경우): Enter 등으로 저장 트리거 직후 애니메이션 지속시간 이내(예: 80ms)에 캡처
  - 빈 상태처럼 실 데이터로 재현 안 되는 상태는 `page.evaluate()`로 강제 연출
  - 목업에 붙어 있는 검토용 요소(검토 바 · 기획 주석 박스 · 데이터 출처 표시 등)는 캡처 전에 `page.add_style_tag()`로 숨긴다. 팝업 · 토스트가 다음 캡처를 덮지 않게 닫고 찍는다.
  - 번호 박스 두 개가 같은 왼쪽 위 모서리에서 시작하면 배지가 겹쳐 하나가 가려진다. 박스 대상을 안쪽 요소(예: 첫 카드 대신 둘째 카드의 이미지)로 바꿔 캡처한다. 넓고 납작한 요소(헤더 전체 등)는 필요한 부분만 크롭해야 글씨가 읽힌다.
  - 순위 태그 · 상태 배지처럼 배지(지름 약 0.5cm)보다 작은 요소에 박스를 걸면 배지가 그 글자를 덮는다. 캡처 후 그 박스 좌표를 왼쪽 · 위로 넓혀(예: x −30px, 폭 +34px, 위아래 4px) 배지가 요소 바깥에 오게 하고, 같은 종류가 여러 개면 맨 앞이 아닌 두 번째 것을 대상으로 잡는다.
  - 표 행처럼 요소가 빽빽한 캡처는 박스를 넓혀도 배지가 옆 글자를 덮는다. 박스는 실제 글자 · 버튼 범위(Range의 getClientRects 합)에 딱 맞추고, 배지는 박스 바깥 빈 쪽(위 · 왼쪽 · 오른쪽)에 박스별로 따로 놓는다(META에 배지 위치를 같이 저장). 슬라이드를 (1/2) · (2/2)로 나누면 각 장에는 그 장에서 설명하는 번호의 박스만 그린다. 접힌 영역 안의 요소를 가리켜야 하면 펼친 상태로 캡처한다.
  - 위로 열리는 툴팁(`bottom: 100%`)과 아래로 열리는 팝업(`top: 100%`)은 크롭 방향(`extra_top` vs `extra_bottom`)이 다르다 — 특히 sticky 헤더 안의 아이콘은 위로 열면 스크롤 영역 밖으로 잘리므로 CSS 자체를 아래로 열리게 뒤집어야 할 수 있음.

### 2. 빌드 스크립트 작성
```python
import sys
from pathlib import Path
HERE = Path(__file__).parent
# [프로젝트 전용 사본] sb_helpers 는 이 프로젝트 폴더 안에 있다.
#   고쳐도 다른 프로젝트 SB 에는 영향이 없다 (프로젝트마다 사본을 둔다).
sys.path.insert(0, str(HERE.parent))
from sb_helpers import *

prs = new_presentation()

build_cover_slide(prs, "제목 — 화면설계 스토리보드", "Ver 1.0 / YYYY-MM-DD / ...", [
    "버전 관리",
    "SB-01  개요 — ...",
    "SB-02  ... — 컬럼 명세",
    ...
])

build_version_slide(prs, [
    ("v1.0", "YYYY-MM-DD", "최초 작성 — SB-01 개요, SB-02 ..."),
    # 기존 SB를 갱신하는 경우 기존 이력 행을 그대로 두고 새 버전 행을 이어서 추가한다 (덮어쓰지 않는다)
])

slide1 = new_slide(prs)
add_header(slide1, "SB-01", "...", "신규 개발")
add_summary(slide1, [[...좌측 불릿...], [...우측 불릿...]], height=2.6, size=9.5)
# 필요하면 add_rect/add_oval_badge로 목업 스크린샷 위에 번호 지시선 직접 그리기

build_column_slide(prs, "SB-02", "품절관리", img_path, crop_w, crop_h, boxes_px_rel, items,
                    legend_labels=["어드민 화면명: URL", ...])

# 표가 아닌 일반 화면 영역: 왼쪽 캡처 + 번호 박스, 오른쪽 번호 설명 (항목이 많으면 below=True 로 캡처 아래까지 이어 씀)
build_screen_slide(prs, "SB-0N", "재주문 체크 · 목록", "신규 개발", ["요약 한 줄"], img_path, crop_w, crop_h,
                   boxes_px_rel, [(1, "영역 제목", ["「다시 주문하실 때인가요?」"]), ...], img_w=18, below=True)

build_states_slide(prs, "SB-0N", "(1/M)", [[item1, item2, item3], [item4, item5]],
                    state_dir=STATE_DIR, img_max_h=4.4)

# 분기가 있는 동작(업로드·저장 검증·결제·승인 등)은 글만 쓰지 말고 플로우차트 슬라이드로
build_flow_slide(prs, "SB-0N", "... · 업로드 동작", [
    {"text": "업로드 저장 클릭", "kind": "start"},
    {"text": "파일 선택됨?", "kind": "decision", "down": "예",
     "side": {"text": "알럿 ① · 중단", "label": "아니오"}},
    {"text": "확인창 ②", "kind": "process", "down": "확인",
     "side": {"text": "취소 · 변경 없음", "label": "취소", "tone": "neutral"}},
    {"text": "실패 행 있음?", "kind": "decision", "down": "아니오",
     "side": {"text": "전체 취소 · 알럿 ③", "label": "예"}},
    {"text": "저장 · 알럿 ④", "kind": "end"},
], [
    (1, "파일 미선택", ["알럿 「업로드할 파일을 선택해 주세요.」"]),
    ...  # 번호는 그림 안 ①~과 맞추고, 문구 원문은 여기에만 「」로
])

prs.save(OUT_PATH)
```
- `items` 튜플은 `(번호, 제목, 설명, is_check)` — `is_check`는 `False`로 둔다(확인 필요 항목은 아래 규칙대로 MD 체크리스트로).
- **확인 필요 항목은 SB 본문에 ★로 남기지 않는다.** 다른 팀(개발 · 데이터 등)이 답해야 하는 사실 확인은 기획 문서(MD) 맨 아래 「확인 필요」 체크리스트에 담당 팀별로 모은다(`- [ ] 내용 (SB-06)`). SB에는 확정된 내용만 적고, `is_check`는 기본 `False`로 둔다. 회신이 오면 SB 설명에 확정 내용을 채우고 체크리스트에서 지운다.
- **현행 기능은 「현행 ○○ 그대로」 한 마디로 끝낸다.** 현행 로직 · 현행 팝업 문구 · 현행 카드 구성을 풀어 쓰면 새로 바꾸는 요건처럼 읽힌다. 조건을 자세히 적는 건 새로 만드는 로직뿐이다.
- **화면 범위를 요약 박스 첫 줄에 적는다.** 기존 화면에 영역만 더하는 경우 「AI 영역은 ○ · ○ · ○ N곳. 나머지는 현행 그대로」처럼 손대는 곳과 안 대는 곳을 같이 적는다.
- **엠대시(—) 금지.** 제목 · 표지 · 설명 모두 가운뎃점(·) · 쉼표 · 괄호로 구분한다.
- 값이 원본을 그대로 보여주는 컬럼과, 산식으로 계산되어 나오는 컬럼을 구분한다 — 계산되는 컬럼(예: 비율·합산값)은 화면에 헤더 옆 정보 아이콘으로 산식 툴팁을 노출하고, SB 설명에도 정확한 산식(조건문 포함)을 적을 것.
- 인터랙션 상태는 한 슬라이드에 2행(각 2~3열)까지가 안전하다(`img_max_h=4.4` 기준 — 슬라이드 높이 초과). 항목이 넘치면 부록으로 빼지 말고 슬라이드 자체를 (N/총장수)로 나눌 것.
- **분기가 있는 동작은 플로우차트를 함께 넣는다** — 업로드·저장 검증·결제·승인처럼 조건에 따라 결과가 갈리는 동작(갈림길 2개 이상)은 글로만 나열하지 말고 `build_flow_slide`로 왼쪽 플로우차트 + 오른쪽 번호 설명 슬라이드를 만든다. 글만 있으면 검사 순서(예: 양식 오류는 확인창 전에 막고, 행 실패는 저장 단계에서 걸림)가 안 보인다. 판단은 마름모, 중단·실패는 빨간 테두리, 정상 흐름은 파란 테두리. 그림 안에는 짧은 라벨과 번호(①~)만 넣고, 알럿·확인창 문구 원문과 실패 사유는 오른쪽 설명에만 「」로 적는다(같은 문구를 두 번 쓰지 않는다). 「실패 처리」처럼 결과를 뭉뚱그리지 말고, 실패로 보는 조건·사유 문구·화면 반응(알럿·취소 범위·실패 사유 파일 열)을 각각 적는다.
- 설명 문장은 한 줄에 한 문장씩 문단을 나눈다(「」 · 괄호 안의 마침표는 나누지 않음). 한 문장이 줄바꿈되면서 끝 몇 글자(「음.」 · 「하나만.」 · 「).」 등)만 다음 줄로 떨어지면, 그 문장을 둘로 나누거나 줄여서 없앤다. 제목 / 부제처럼 짝으로 적는 문구도 한 줄씩 따로 쓴다. 문장을 나누면 설명이 길어지므로, `build_states_slide` 처럼 설명 칸 높이가 고정된 슬라이드는 행 높이를 설명 길이에 맞춰 다시 계산하고(다음 행 침범 방지) 이미지 · 표를 설명 아래에 붙인 슬라이드는 위치를 다시 확인한다.
- 목업 검토용 정보는 SB에 쓰지 않는다: 가상 병원 · 테스트 계정 이름, 캡처에 쓴 케이스 · 검색어(「캡처: 가상 병원 7」, 「검색어 「린코」」 등). 개발자는 그걸로 만들 게 없다. 상태는 「도래 있는 회원」 · 「고정 품목을 담은 직후」처럼 조건으로만 적는다.
- 논의 중 빼기로 한 것을 「~는 표시하지 않음」 · 「(토스트 없음)」 · 「(넘김 없음)」처럼 부정형으로 남기지 않는다. 개발자는 결과만 보므로 있는 것만 적는다. 단, 조건에 따른 규칙(「5개 이하면 넘김 없음」)이나 동작 규칙(「체크는 바뀌지 않음」)은 결과라서 적는다.
- SB 텍스트에는 산출물 자체에 대화 흔적을 남기지 않는다 — 왜 이렇게 정했는지 논의 서사 없이 결론(판정 공식, 데이터 출처, 식별자 등)만 담백하게 적는다.
- 기존 SB를 수정하는 경우 버전 관리 표에 새 행(버전·일자·변경 내용)을 추가하고 파일명도 버전을 올린다(`_v1.0` → `_v1.1` 등) — 이전 행은 지우지 않는다.

### 3. 렌더 확인 (자체 검수 루프)
```python
from sb_helpers import close_if_open, render_slides_to_png
close_if_open(OUT_PATH)          # PowerPoint에서 열려있으면 안전하게 닫기
# ... prs.save(OUT_PATH) 재실행 ...
pngs = render_slides_to_png(OUT_PATH, out_dir, slide_numbers=[1, 2, 3])
```
내보낸 PNG를 직접 열어 다음을 확인한다:
- 텍스트가 박스/이미지 밖으로 넘치지 않는지 (특히 불릿·설명 텍스트가 길어졌을 때)
- 캡처 글자가 읽히는지: 상태 슬라이드 한 칸에 세로로 긴 캡처(목록 전체 등)를 넣으면 작아져서 못 읽는다. 설명할 부분만 크롭하고(예: 펼친 묶음 하나), 그래도 작으면 슬라이드를 (1/2) · (2/2)로 나눠 긴 캡처끼리 한 장에 크게 둔다.
- 캡처와 설명 사이가 벌어지지 않는지: 납작한 캡처는 고정 높이 칸 가운데에 놓지 말고 칸 위쪽에 붙이고 설명은 그 행에서 가장 큰 캡처 바로 아래로(`build_states_slide` 기본 배치는 가운데라 벌어짐). 전체 화면 슬라이드의 영역 목록은 슬라이드 오른쪽 끝이 아니라 캡처 바로 오른쪽에
- 배지 번호가 인접 도형에 가려지지 않는지, 반대로 배지가 작은 태그 · 글자를 덮지 않는지(덮으면 박스를 넓혀 배지를 요소 바깥으로)
- 표지 TOC가 실제 슬라이드 구성과 일치하는지

겹침/오버플로 발견 시 텍스트를 줄이거나 박스 높이·이미지 위치를 조정하고 2단계부터 반복.

### 4. 원 요구사항 대조 + 정량 검증
- 원본 요구사항 문서가 있으면 항목별로 전부 커버됐는지 대조한다. 빠진 게 있으면 왜 빠졌는지(스코프 제외 확정인지, 그냥 누락인지) 확인 후 반영하거나 "이번 스코프 제외"로 명시적으로 처리한다.
- SB에 적은 산식·조건문을 원본 문서와 한 번 더 대조해서 AND/OR, 경계값(이상/초과), 예외 케이스(0으로 나누기 등)를 놓치지 않았는지 확인한다.
