# QA 자동화 — 기획서 기준 화면 검수

구현된 화면이 확정 기획서대로 만들어졌는지 검증하고 HTML 리포트를 만든다.

핵심은 **판정 근거를 확정 산출물에 묶는 것**이다. 기획서에 없는 걸 "당연히 이래야지"로 넣으면 개발팀이
납득하지 못하고, 근거가 있는 진짜 결함까지 같이 흐려진다. 그래서 케이스마다 원본 위치를 붙인다.

스킬 폴더를 `$SKILL` 로 표기한다. 이 SKILL.md 가 있는 폴더이며, 러너는 `$SKILL/qa_auto/qa_run.py` 다.

## 3단계로 나누는 이유

```
[1] 케이스 생성   Claude   기획서·Figma·SB → 자연어 테스트 케이스 MD   → 사람 검토
[2] 셀렉터 매핑   Claude   실제 사이트 탐색 → 실행 스펙 JSON
[3] 실행·리포트   Python   스펙 반복 실행 → HTML 리포트
```

기획서만 보고 바로 실행 스크립트를 뽑는 건 불가능하다. 실제 DOM 셀렉터를 모르기 때문이다.
그리고 이렇게 끊어두면 **화면이 안 바뀌는 한 3단계만 반복**하면 되므로, 회귀 검사는 Claude 없이도
돌릴 수 있다 (아래 `--init` 이 만들어주는 `run_qa.bat` 더블클릭).

## 준비물

1. **구현된 화면 URL** — 운영인지 스테이징인지 확인한다.
2. **확정 기획 자료** — MD·HTML 목업·docx·xlsx·PDF·Figma·SB(PPTX) 중 가진 것 전부.
3. **파이썬 의존성**: `playwright` (+ `py -m playwright install chromium`). 없으면 설치를 안내한다.
4. **로그인이 필요하면 세션**: Claude 가 로그인 창을 띄우고 사용자는 로그인만 한다. 아래 "로그인 처리" 참고.

## 시작 전 확인

아래가 불명확하면 먼저 묻고 시작하지 않는다.

1. **대상 URL** (운영/스테이징 명시)
2. **기획 자료 경로** — 여러 개면 전부
3. **범위** — 화면 전체인지 특정 기능만인지

## $SKILL 경로 찾기

`$SKILL` 은 이 SKILL.md 가 있는 폴더다. 러너는 `$SKILL/qa_auto/qa_run.py` 다.

**사용자에게 이 경로를 묻지 않는다.** 설치 위치는 사람마다 다르고 본인도 모르는 게 정상이다.
이 SKILL.md 를 읽은 실제 경로를 그대로 쓰고, 그게 불분명하면 직접 찾는다.

```bash
# 플러그인으로 설치된 경우 (대부분)
ls ~/.claude/plugins/marketplaces/*/plugins/qa-test/skills/qa-test/qa_auto/qa_run.py
# 스킬 폴더에 직접 둔 경우
ls ~/.claude/skills/qa-test/qa_auto/qa_run.py
```

아래 명령들은 **Claude 가 절대경로를 채워서 직접 실행한다.** 사용자가 경로를 타이핑하게
만들지 않는다. `--login` 도 마찬가지다 (백그라운드로 실행하고, 사용자는 뜬 창에서 로그인만 한다).

## 작업 폴더

산출물은 **검수 대상 기획이 들어있는 폴더 안**에 만든다. 스킬 폴더에는 아무것도 쓰지 않는다.

```
py "$SKILL/qa_auto/qa_run.py" --init <기획_폴더>
```

`<기획_폴더>` 는 그 기획의 자료가 모여 있는 곳이다 (예: `projects/재고_대시보드`).
저장소 루트나 `tools/` 밑이 아니라 **기획 폴더 바로 아래**에 둔다 — 기획을 남에게 넘길 때
폴더째 주면 테스트 케이스와 스펙이 같이 따라가야 하기 때문이다. 기획마다 따로 만든다.

이미 `qa_auto/` 가 있으면 다시 돌려도 안전하다 (기존 스펙·케이스는 건드리지 않고
`run_qa.bat` 만 현재 설치 경로로 새로 만든다 — 플러그인을 재설치해 경로가 바뀌었을 때 쓴다).

`run_qa.bat` 은 스킬 패키지에 들어있지 않고 **이때 만들어진다** — 팀원마다 스킬 설치 경로가
다르므로, 러너의 절대경로를 그 자리에서 박아 넣어야 더블클릭이 동작하기 때문이다.

생기는 구조:

```
qa_auto/
├── specs/       실행 스펙 JSON   ← 2단계 산출
├── cases/       테스트 케이스 MD ← 1단계 산출
├── fixtures/    업로드 테스트용 파일 (없으면 스킬 번들 기본값 사용)
├── output/      리포트 + 스크린샷 ← 3단계 산출
└── run_qa.bat   더블클릭 실행 (러너 경로가 박혀서 생성됨)
```

## 로그인 처리

로그인이 필요하면 **방법을 고르게 하지 않고 바로 로그인 창을 띄운다.** Claude 가 아래 명령을
백그라운드로 실행하고, 사용자에게는 "뜬 창에서 로그인만 하면 저절로 닫힌다"고만 알린다.

```
py "$SKILL/qa_auto/qa_run.py" --login <URL> [<URL2> ...] --ws "<기획_폴더>/qa_auto"
```

- 로그인이 끝난 걸 화면으로 감지하면 세션을 저장하고 **창이 저절로 닫힌다.** 사용자가 창을 닫거나
  콘솔로 돌아갈 일이 없다. 끝나면 백그라운드 작업 완료 알림이 온다.
- **사이트가 여러 개면 주소를 이어서 준다** (예: 프론트 + 어드민). 하나가 로그인되는 대로 같은 탭이
  다음 주소로 넘어간다.
- 기존 `auth.json` 을 불러와서 시작하므로, 세션이 살아 있는 사이트는 바로 통과하고 빠진 사이트만
  로그인하면 된다. 세션 갱신도 같은 명령이다.
- 감지 기준: 비밀번호 칸과 글자가 딱 "로그인"인 링크·버튼이 둘 다 안 보이고 본문이 채워진 화면이
  두 번 연속 확인되면 로그인으로 본다. 맞지 않는 사이트면 `--done-text 로그아웃` 처럼 로그인했을
  때만 보이는 문구를 준다.
- 저장 중에 화면이 깜빡이지 않는다 (`storage_state()` 를 쓰지 않고 쿠키와 열린 탭의
  localStorage 만 읽는다). **이 방식을 `storage_state()` 주기 저장으로 되돌리지 않는다.**
  열려 있지 않은 출처를 읽으려고 숨은 탭을 띄웠다 닫아서, 2초마다 화면이 깜빡인다.

세션은 `qa_auto/auth.json` 에, 로그인 당시 브라우저 UA 는 `qa_auto/auth.meta.json` 에 저장된다.
스펙 `meta` 에 `"auth": "auth.json"` 을 넣으면 러너가 둘 다 쓴다. **세션을 UA 에 묶는 사이트가
있어서(블루닥) 헤드리스 기본 UA(`HeadlessChrome`)로 열면 쿠키가 살아 있어도 비로그인으로 보인다.**
세션 상태를 직접 확인하는 스크립트를 짤 때도 `auth.meta.json` 의 UA 를 `user_agent` 로 넣는다.
이걸 빼고 확인해서 "로그인 실패"로 단정하지 않는다.

`qa_auto/cookies.txt` (개발자도구 쿠키 표 붙여넣기)는 로그인 창을 띄울 수 없는 환경(원격 세션 등)
이거나 사용자가 직접 원할 때만 쓴다. 먼저 제안하지 않는다.

> 세션은 사용자가 직접 로그인해서 만든다. 아이디·비밀번호를 받아 입력하거나, 크롬 프로필을
> 복사하는 식의 우회는 하지 않는다.

**스펙에 `login_check` 를 반드시 넣는다.**

```json
"login_check": { "body_contains": "인증이 필요한 관리자 페이지" }
```

세션이 만료되면 모든 케이스가 엉뚱한 이유로 줄줄이 실패해서 원인 파악에 시간이 걸린다.
이 조건이 있으면 첫 페이지에서 바로 잡아 중단하고 갱신 방법을 안내한다.
로그인된 상태와 안 된 상태를 실제로 한 번씩 열어보고 구분되는 문구를 고른다.

> 로그인 페이지가 떴을 때 **아이디·비밀번호를 받아 자동 로그인을 시도하지 않는다.** 멈추고
> 로그인 창을 다시 띄운다.

## 1단계 — 테스트 케이스 생성

### 자료 읽기

| 포맷 | 방법 |
|---|---|
| MD / HTML | Read. **HTML 목업은 `data-tip`·`data-filter` 같은 속성 원문이 가장 정확한 근거**다 |
| docx / xlsx / PDF / PPTX | 문서 추출 MCP(`xberg` 등)로 텍스트 추출 |
| Figma | Figma MCP. 이미 받아둔 스크린샷이 로컬에 있으면 그걸 먼저 본다 (호출 한도 절약) |

여러 자료가 있으면 전부 읽고 통합한다. 기획서에 없고 Figma에만 있는 문구, SB 디스크립션에만 있는
예외 처리가 자주 있다.

**자료 간 날짜를 반드시 확인한다.** 가장 최신 확정본이 판정 기준이다. 오래된 Figma나 구버전 목업을
기준으로 삼으면 멀쩡한 구현을 결함으로 보고하게 된다. 파일명이 비슷한 구버전이 같은 폴더에 있는
경우가 흔하므로 수정 시각을 확인할 것.

### 케이스 도출

- **근거 없는 케이스는 만들지 않는다.** 케이스마다 원본 위치(`파일명 > 섹션`)와 요건 원문을 붙인다.
  카테고리를 채우려고 "로딩 속도 확인" 같은 일반론을 넣지 않는다.
- **화면에서 눈으로 확인 가능한 것만.** "유지보수성 개선" 같은 목적 서술은 제외한다.

아래 유형을 우선 훑는다. 기획서에서 가장 자주 누락·오구현되는 지점이다.

| 유형 | 무엇을 찾나 |
|---|---|
| 고정 수치 | px 사이즈, 최대 개수, 글자수 제한 → 경계값 ±1 |
| 알럿·문구 | 기획서 문구와 **토씨까지** 일치하는지 |
| 조건부 노출 | "~인 경우에만" → 노출 O 케이스와 X 케이스 둘 다 |
| 토글·상태 전환 | 기본값, 전환 시 동작, 되돌렸을 때 동작 |
| 순서 | 등록 순서대로 노출되는지, 순서변경이 동작하는지 |
| **연속 사용 흐름** | 새로고침 없이 A→B로 이어서 조작했을 때. 아래 참고 |
| **삭제·통합 지시** | "A는 B에 포함시킨다", "C 컬럼은 뺀다" → **없어야 할 것이 없는지**가 핵심 |
| 범위 제외 | "이번 범위 아님"으로 명시된 것이 화면에 없는지 |

"삭제·통합 지시"와 "범위 제외"가 특히 중요하다. 기획 변경은 "추가"보다 "통합·삭제" 지시가
누락되기 쉽고, 그런 건 화면만 봐서는 잘 안 보인다.

**연속 사용 흐름** — 사용자는 중간에 새로고침하지 않는다. 매번 새로고침 후 한 번만 누르는
케이스만 있으면, 이전 상태가 안 지워지거나 건수가 재계산되지 않는 종류의 버그는 영원히 안 걸린다.

- 먼저 그 요소가 **교체식(단일선택)인지 누적식(다중선택)인지** 확인한다. 기대값이 정반대다.
  교체식은 A→B 후 **B만**, 누적식은 **A∪B** 가 남아야 한다.
- 해당 케이스에 `chains: true` 를 준다. 실패했을 때 러너가 단독 재현으로
  "이어서 해서 깨진 건지 원래 깨진 건지"를 가려 사유에 적어준다.
- **흐름을 길게 늘이지 않는다.** 스텝이 하나 깨지면 그 케이스는 거기서 끝나고 뒤 스텝은
  실행되지 않는다. 열 개를 한 케이스에 몰면 두 번째에서 깨졌을 때 나머지 여덟 개가 정상인지
  알 수 없다. 2~3동작 단위로 끊는다.
- 규격·문구처럼 상태와 무관한 검증은 **단건 케이스로 둔다.** 흐름으로 묶을 이유가 없다.

### 쓰기 판정

각 케이스가 서버에 데이터를 쓰는지 표시한다. 저장·등록·삭제·수정 버튼을 누르면 쓰기다.

**승인을 대신 판단하지 말고 `승인: ☐` 상태로 두고 넘긴다.** 쓰기 케이스에는 정리(cleanup) 절차를
반드시 같이 설계한다 — 없으면 러너가 실행을 거부한다.

### 산출

`<기획_폴더>/qa_auto/cases/{프로젝트명}.md` 에 케이스별로 요건·근거·분류·쓰기여부·승인·절차·기대결과·정리를 적는다.

작성 후 **사람에게 검토를 요청하고 멈춘다.** 승인 없이 2단계로 넘어가지 않는다.

## 2단계 — 셀렉터 매핑

1. Playwright로 대상 페이지에 접속한다. 로그인이 필요하면 `auth.json` 과 `auth.meta.json` 의 UA 를 쓴다.
2. 각 케이스의 절차를 실제로 밟아보며 **DOM 셀렉터를 확인한다. 추측으로 쓰지 않는다.**
3. 이때 **쓰기 액션은 실행하지 않는다.** 셀렉터만 읽고 지나간다.
4. `$SKILL/qa_auto/spec_schema.md` 포맷에 맞춰 `<기획_폴더>/qa_auto/specs/{프로젝트명}.json` 을 쓴다.

### 지킬 것

- `approved` 는 **전부 `false`** 로 둔다. 사람이 직접 켠다.
- **로그인 상태가 다른 화면(비회원 · 회원 · 어드민)도 스펙 하나로 쓴다.** 스펙을 나누면 리포트와
  웍스 로그가 따로 나와 같은 결함이 두 번 실린다. `meta.sessions` 에 세션을 두고 케이스에
  `session` 을 준다 (`spec_schema.md` "세션 여러 개"). 프론트와 어드민을 한 세션으로 오가면
  `login_check` 를 `when_url` 로 나눈다.
- **케이스마다 `area`·`fix` 를 적는다.** 검수 결과는 기획팀이 웍스에 글로 올려 넘기는데,
  `fix` 가 그 글의 한 줄이 된다. 명사형으로 끊고(`추가`·`삭제`·`변경`), 바뀌는 값은
  `현재 > 목표` 로 쓴다. `~해주세요` 로 쓰면 요청이 아니라 제안으로 읽혀 일이 안 돌아간다.
- **케이스마다 `kind` 를 정한다.** 기획팀이 리포트를 먼저 보고 개발팀에 넘길 것만 추리는데,
  그 선을 여기서 긋는다. `defect`(확정 기획서 근거 있음, 기본값) / `improve`(사용성 제안) /
  `gap`(기획서에 정의 없음). `source` 에 확정 자료 위치를 못 적겠으면 `defect` 가 아니다.
- 한글 버튼은 `label` 필드에 버튼 텍스트를 넣는다 — 러너의 쓰기 자동 판정이 이 값을 본다.
  `#save` 같은 영문 셀렉터만으론 쓰기인지 알 수 없다.
- `blocklist` 에 절대 눌리면 안 되는 버튼을 넣는다. 기본: `발송`, `결제`, `발주`, `일괄삭제`, `권한`.
- **순서·계산 판정은 `expect_js` 를 쓴다.** CSS 인접 선택자(`+`)는 DOM 형제만 보므로, 필터로 숨긴
  행을 건너뛴 "화면에 보이는 순서"를 검사하지 못해 **거짓 통과**가 난다. 자동화에서 가장 위험한
  실패는 실패를 놓치는 게 아니라 통과라고 잘못 보고하는 것이다.
- 툴팁이 `title` 속성이 아니라 JS로 생성되는 경우가 많다. `hover` 액션으로 띄운 뒤 실제 툴팁
  요소를 `expect_text` 로 검사한다.
- **결함 증빙 스크린샷은 문제 지점만 찍지 않는다.** `screenshot` 에 `selector` 와 `context` 를 주어
  주변 정상 행·헤더가 같이 담기게 한다. 전체 화면 한 장으로는 수백 행 중 어디가 문제인지 아무도
  못 찾는다.
- 인라인 편집은 `dblclick` → `type` → `press Enter` 로 밟는다. `fill` 은 더블클릭 이후에 생기는
  input 을 못 잡는다.
- 엑셀 내보내기는 `download` + `expect_file` 로 검증한다. 기대 행수는 `row_count_js` 로 화면에서
  읽어 비교한다 — 운영 데이터는 계속 바뀌므로 고정값을 박을 수 없다.

### 검증

```
py "$SKILL/qa_auto/qa_run.py" qa_auto/specs/{프로젝트명}.json --dry-run
```

읽기 케이스가 셀렉터 문제로 실패하면 고치고 다시 돌린다. 여기서 통과해야 넘긴다.

## 3단계 — 실행·리포트

```
py "$SKILL/qa_auto/qa_run.py" qa_auto/specs/{프로젝트명}.json
```

팀원은 `qa_auto/run_qa.bat` 더블클릭으로 같은 일을 한다.

리포트는 `qa_auto/output/{프로젝트}_{일시}/` 에 생긴다. 스크린샷은 클릭하면 확대되고
`원본 크기` 버튼으로 1:1 확인이 된다.

| 파일 | 누가 보나 |
|---|---|
| `리포트.html` 의 **기획팀 검토** 탭 | 전체 케이스. 통과는 접혀 있고 눌러서 펼친다 |
| `리포트.html` 의 **개발 전달용** 탭 | 웍스에 올릴 로그 + 항목별 근거. `복사` 버튼 있음 |
| `웍스등록.txt` | 위 로그와 같은 내용. 웍스에 그대로 붙여넣는 용도 |
| `개발전달.md` | 근거·재현 절차·스크린샷 경로까지 담은 상세본 |

로그는 **지시문만** 싣는다. 근거·재현 절차는 상세본에 남긴다. 설명이 붙으면 받는 쪽이
"추가 검토 요청"으로 읽어 일이 안 돌아간다.

개발 전달용에는 `improve`·`gap` 이 안 들어간다. 기획 확정이 안 끝난 항목까지 같이 넘기면
근거가 확실한 결함까지 같이 흐려지기 때문이다. 대신 "전달에서 뺀 항목" 으로 목록만 보여준다.

### 케이스 상태

| 상태 | 뜻 | 조치 |
|---|---|---|
| `PASS` | 기획서대로 구현됨 | — |
| `FAIL` | 기획서와 구현이 다름 | 실패 스크린샷 확인 후, `kind` 에 따라 개발 전달 / 기획팀 보류 |
| `SKIPPED` | 쓰기 미승인 | 검토 후 스펙에서 `approved: true` |
| `BLOCKED` | blocklist 또는 cleanup 누락 | 스펙 수정 필요 |

`FAIL` 이 곧 결함은 아니다. 셀렉터가 낡았을 수도 있으니 스크린샷을 먼저 본다.

## 리포트 전 — "화면만으로는 안 됨" 재검토

리포트를 내기 전에, 검증을 포기하고 빼둔 항목을 **반드시 한 번 더 훑는다.**

처음 분류할 때는 보통 (1) 로그인 세션이 없고 (2) 원천 데이터를 가진 다른 화면을 아직 안 봤다.
그 시점의 "못 한다"는 판단이 그대로 굳어서 **검수 범위가 통째로 빠진다.** 조건이 바뀌었는데
재검토하는 단계가 없으면 아무도 다시 안 본다.

항목마다 아래를 확인한다.

- **파일을 받아서 열면 되는가** — 엑셀·CSV·PDF 다운로드는 Playwright 로 받아 파싱하면
  행수·컬럼·순서까지 화면과 대조된다. "파일 비교라서 불가"는 대개 틀린 판단이다.
- **원천을 가진 다른 화면이 있는가** — 관리자 상세 화면이 URL 파라미터로 단건 조회를 지원하면
  (`?code=12345` 같은) 계산 결과가 아니라 **산식 자체**를 검증할 수 있다. 화면 검수에서 가장
  값어치가 큰 영역이라 빠뜨리면 손해가 크다.
- **시간만 있으면 되는가** — 갱신 주기 같은 건 간격을 두고 스냅샷을 두 번 찍으면 된다.

정말로 안 되는 것만 남긴다. 남길 때는 **왜 안 되는지 한 줄을 적는다.** "개발팀 확인"처럼
뭉개지 않는다 — 그렇게 적으면 다음 사람도 똑같이 건너뛴다.

## 안전장치

운영 서버를 대상으로 하므로 쓰기에 잠금이 걸려 있다. 러너가 강제하며 우회할 수 없다.

| 장치 | 동작 |
|---|---|
| 승인 게이트 | 쓰기 케이스는 `approved: true` 가 있어야만 실행. 없으면 `SKIPPED` |
| blocklist | 발송·결제 등은 승인 여부와 무관하게 `BLOCKED` |
| cleanup 강제 | 쓰기 케이스에 정리 절차가 없으면 실행 거부. 테스트가 실패해도 정리는 항상 시도 |
| QA 프리픽스 경고 | 입력값에 `[QA]YYYYMMDD` 가 없으면 리포트에 경고 |
| `expect_js` 읽기 전용 | `.click(`·`.value =`·`fetch(` 등이 있으면 거부 — JS로 승인 게이트를 우회하지 못하게 |

`--dry-run` 은 이 위에 한 겹 더 얹어, 승인된 케이스라도 쓰기 스텝을 전부 건너뛴다.

> **`approved` 를 임의로 켜지 않는다.** 사용자가 명시적으로 지시한 케이스만 켠다.

## 주의

- 스펙 작성·검증 중에도 저장/등록/삭제 버튼을 누르지 않는다.
- 세션 만료로 로그인 페이지가 뜨면 **즉시 멈추고 로그인 창을 다시 띄운다. Claude 가 로그인 시도를 하지 않는다.**
- 기획서와 구현이 다르면 그게 곧 테스트 실패다. 임의로 기획서 쪽을 맞춰 해석하지 않는다.
- 가상 스크롤(tui-grid 등)을 쓰는 화면은 DOM에 일부 행만 있다. 전수 확인이 필요하면 검색·필터로
  대상을 좁히거나 스크롤을 돌려야 한다. 보이는 행만 보고 "그런 값 없음"이라고 단정하지 말 것.

## 수기 검수 항목 분류

사용자가 직접 검수한 항목 목록을 주면, 각각을 확정 기획서와 대조해 나눈다.

| 분류 | 판단 기준 | 처리 |
|---|---|---|
| **결함** | 확정 기획서에 있는데 구현에 없음 | 회귀 스펙에 케이스 추가 |
| **개선 요청** | 기획서에 근거 없음 | **별도 스펙 파일**로 분리 |
| **재현 안 됨** | 확인했으나 재현 실패 | 조건(화면폭·배율·데이터)을 되물음 |
| **화면만으로는 안 됨** | 화면 밖 경로가 필요 | 아래 재검토를 거친 뒤에만 남김 |

마지막 분류를 **"자동화 불가"라고 부르지 않는다.** 불가능한 게 아니라 **경로가 다를 뿐**인
경우가 대부분이고, 이름을 그렇게 붙이면 검증을 시도조차 안 하게 된다.

개선이 **한두 건**이면 스펙을 나누지 말고 해당 케이스에 `kind: "improve"` (또는 `"gap"`) 만
달아둔다. 리포트가 개발 전달용에서 알아서 빼준다.

**스펙을 분리하는 이유**: 개선 요청은 아직 구현 전이라 전부 실패로 나온다. 회귀 검사와 섞으면
"항상 빨간 리포트"가 되어 진짜 결함이 묻힌다. 분리하면 개선 스펙은 구현 진척 추적용으로,
회귀 스펙은 "전부 통과가 정상"인 상태로 각각 의미를 갖는다.

개발팀에 전달할 때도 결함과 개선을 나눠 보내라고 안내한다. 결함은 근거가 명확해 이견이 적고,
개선은 일정 협의가 필요해 성격이 다르다.
