# QA 자동화 — 기획서 기준 화면 검수

구현된 화면이 확정 기획서대로 만들어졌는지 검증하고 HTML 리포트를 만든다.

핵심은 **판정 근거를 확정 산출물에 묶는 것**이다. 기획서에 없는 걸 "당연히 이래야지"로 넣으면 개발팀이
납득하지 못하고, 근거가 있는 진짜 결함까지 같이 흐려진다. 그래서 케이스마다 원본 위치를 붙인다.

스킬 폴더를 `$SKILL` 로 표기한다. 이 SKILL.md 가 있는 폴더이며, 러너는 `$SKILL/qa_auto/qa_run.py` 다.

## 3단계로 나누는 이유

```
[1] 케이스 생성   Claude   기획서·Figma·SB → 자연어 테스트 케이스 MD   → 사람 검토
[2] 셀렉터 매핑   Claude   실제 사이트 탐색 → 실행 스펙 JSON
[3] 실행·리포트   Python   스펙 반복 실행 → HTML 리포트
```

기획서만 보고 바로 실행 스크립트를 뽑는 건 불가능하다. 실제 DOM 셀렉터를 모르기 때문이다.
그리고 이렇게 끊어두면 **화면이 안 바뀌는 한 3단계만 반복**하면 되므로, 회귀 검사는 Claude 없이도
돌릴 수 있다 (아래 `--init` 이 만들어주는 `run_qa.bat` 더블클릭).

## 준비물

1. **구현된 화면 URL** — 운영인지 스테이징인지 확인한다.
2. **확정 기획 자료** — MD·HTML 목업·docx·xlsx·PDF·Figma·SB(PPTX) 중 가진 것 전부.
3. **파이썬 의존성**: `playwright` (+ `py -m playwright install chromium`). 없으면 설치를 안내한다.
4. **로그인이 필요하면 세션**: Claude 가 로그인 창을 띄우고 사용자는 로그인만 한다. 아래 "로그인 처리" 참고.

## 시작 전 확인

아래가 불명확하면 먼저 묻고 시작하지 않는다.

1. **대상 URL** (운영/스테이징 명시)
2. **기획 자료 경로** — 여러 개면 전부
3. **범위** — 화면 전체인지 특정 기능만인지

## $SKILL 경로 찾기

`$SKILL` 은 이 SKILL.md 가 있는 폴더다. 러너는 `$SKILL/qa_auto/qa_run.py` 다.

**사용자에게 이 경로를 묻지 않는다.** 설치 위치는 사람마다 다르고 본인도 모르는 게 정상이다.
이 SKILL.md 를 읽은 실제 경로를 그대로 쓰고, 그게 불분명하면 직접 찾는다.

팀원 bat 과 **같은 러너**를 써야 결과 이력에 버전이 섞이지 않는다. bat 과 같은 순서로 찾는다.

```bash
# 1) 플러그인 설치 경로 (bat 도 이것부터 본다)
py -c "import json,os;j=json.load(open(os.path.expanduser('~/.claude/plugins/installed_plugins.json'),encoding='utf-8'));print(j['plugins']['qa-test@claude-skills'][0]['installPath'])"
#    → <installPath>/skills/qa-test/qa_auto/qa_run.py
# 2) 없으면 marketplaces 클론
ls ~/.claude/plugins/marketplaces/*/plugins/qa-test/skills/qa-test/qa_auto/qa_run.py
# 3) 스킬 폴더에 직접 둔 경우
ls ~/.claude/skills/qa-test/qa_auto/qa_run.py
```

찾은 러너의 `RUNNER_VERSION` 이 이 SKILL.md 옆 러너보다 낮으면 실행하지 말고 사용자에게
플러그인 업데이트를 먼저 안내한다 (bat 도 낮은 버전이면 멈춘다).

아래 명령들은 **Claude 가 절대경로를 채워서 직접 실행한다.** 사용자가 경로를 타이핑하게
만들지 않는다. `--login` 도 마찬가지다 (백그라운드로 실행하고, 사용자는 뜬 창에서 로그인만 한다).

## 작업 폴더

산출물은 **검수 대상 기획이 들어있는 폴더 안**에 만든다. 스킬 폴더에는 아무것도 쓰지 않는다.

```
py "$SKILL/qa_auto/qa_run.py" --init <기획_폴더>
```

`<기획_폴더>` 는 그 기획의 자료가 모여 있는 곳이다 (예: `projects/재고_대시보드`).
저장소 루트나 `tools/` 밑이 아니라 **기획 폴더 바로 아래**에 둔다 — 기획을 남에게 넘길 때
폴더째 주면 테스트 케이스와 스펙이 같이 따라가야 하기 때문이다. 기획마다 따로 만든다.

이미 `qa_auto/` 가 있으면 다시 돌려도 안전하다 (기존 스펙·케이스는 건드리지 않고
`run_qa.bat`·`login_qa.bat` 만 새로 만든다).

`run_qa.bat` 은 **실행할 때 러너를 찾는다** (`installed_plugins.json` 의 설치 경로 → marketplaces
경로 순서). 플러그인을 업데이트할 때마다 설치 경로가 바뀌어서, 경로를 박아 두면 bat 이 죽거나
구버전 러너로 돈다. 둘 다 없으면 "qa-test 플러그인 설치 필요", 찾은 러너가 bat 을 만들 때의
버전보다 낮으면 "qa-test 플러그인 업데이트 필요" 를 띄우고 멈춘다. 팀원 PC 도 플러그인을
업데이트해야 돈다. `login_qa.bat` 은 주소를 비워 두고 Enter 만 누르면 스펙의 검수 주소로 로그인한다.

**기획 폴더를 남에게 폴더째 넘길 때는 `qa_auto/` 의 `auth.json` · `auth.meta.json` · `cookies.*` ·
`output/` 을 빼고 넘긴다.** 앞의 셋은 운영 어드민 로그인 세션이고, `output/` 에는 운영 화면 스크린샷과
동작 기록이 들어 있다. `.gitignore` 는 커밋만 막을 뿐 복사 · 공유드라이브 동기화는 못 막는다.

생기는 구조:

```
qa_auto/
├── specs/       실행 스펙 JSON   ← 2단계 산출
├── cases/       테스트 케이스 MD ← 1단계 산출
├── fixtures/    업로드 테스트용 파일 (없으면 스킬 번들 기본값 사용)
├── output/      리포트 + 스크린샷 ← 3단계 산출 (최근 10회 + 비교 기준만 남기고 정리됨)
├── run_qa.bat   더블클릭 실행 (읽기만)
└── login_qa.bat 로그인 세션 저장
```

## 로그인 처리

로그인이 필요하면 **방법을 고르게 하지 않고 바로 로그인 창을 띄운다.** Claude 가 아래 명령을
백그라운드로 실행하고, 사용자에게는 "뜬 창에서 로그인만 하면 저절로 닫힌다"고만 알린다.

```
py "$SKILL/qa_auto/qa_run.py" --login <URL> [<URL2> ...] --ws "<기획_폴더>/qa_auto"
```

- 로그인이 끝난 걸 화면으로 감지하면 세션을 저장하고 **창이 저절로 닫힌다.** 사용자가 창을 닫거나
  콘솔로 돌아갈 일이 없다. 끝나면 백그라운드 작업 완료 알림이 온다.
- **사이트가 여러 개면 주소를 이어서 준다** (예: 프론트 + 어드민). 하나가 로그인되는 대로 같은 탭이
  다음 주소로 넘어간다.
- 기존 `auth.json` 을 불러와서 시작하므로, 세션이 살아 있는 사이트는 바로 통과하고 빠진 사이트만
  로그인하면 된다. 세션 갱신도 같은 명령이다.
- 감지 기준: 비밀번호 칸과 글자가 딱 "로그인"인 링크·버튼이 둘 다 안 보이고 본문이 채워진 화면이
  두 번 연속 확인되면 로그인으로 본다. 맞지 않는 사이트면 `--done-text 로그아웃` 처럼 로그인했을
  때만 보이는 문구를 준다.
- 저장 중에 화면이 깜빡이지 않는다 (`storage_state()` 를 쓰지 않고 쿠키와 열린 탭의
  localStorage 만 읽는다). **이 방식을 `storage_state()` 주기 저장으로 되돌리지 않는다.**
  열려 있지 않은 출처를 읽으려고 숨은 탭을 띄웠다 닫아서, 2초마다 화면이 깜빡인다.

세션은 `qa_auto/auth.json` 에, 로그인 당시 브라우저 UA 는 `qa_auto/auth.meta.json` 에 저장된다.
스펙 `meta` 에 `"auth": "auth.json"` 을 넣으면 러너가 둘 다 쓴다. **세션을 UA 에 묶는 사이트가
있어서(블루닥) 헤드리스 기본 UA(`HeadlessChrome`)로 열면 쿠키가 살아 있어도 비로그인으로 보인다.**
세션 상태를 직접 확인하는 스크립트를 짤 때도 `auth.meta.json` 의 UA 를 `user_agent` 로 넣는다.
이걸 빼고 확인해서 "로그인 실패"로 단정하지 않는다.

`qa_auto/cookies.txt` (개발자도구 쿠키 표 붙여넣기)는 로그인 창을 띄울 수 없는 환경(원격 세션 등)
이거나 사용자가 직접 원할 때만 쓴다. 먼저 제안하지 않는다.

> 세션은 사용자가 직접 로그인해서 만든다. 아이디·비밀번호를 받아 입력하거나, 크롬 프로필을
> 복사하는 식의 우회는 하지 않는다.

**스펙에 `login_check` 를 반드시 넣는다.**

```json
"login_check": { "body_contains": "인증이 필요한 관리자 페이지" }
```

세션이 만료되면 모든 케이스가 엉뚱한 이유로 줄줄이 실패해서 원인 파악에 시간이 걸린다.
이 조건이 있으면 첫 페이지에서 바로 잡아 중단하고 갱신 방법을 안내한다.
로그인된 상태와 안 된 상태를 실제로 한 번씩 열어보고 구분되는 문구를 고른다.

> 로그인 페이지가 떴을 때 **아이디·비밀번호를 받아 자동 로그인을 시도하지 않는다.** 멈추고
> 로그인 창을 다시 띄운다.

## 1단계 — 테스트 케이스 생성

### 자료 읽기

| 포맷 | 방법 |
|---|---|
| MD / HTML | Read. **HTML 목업은 `data-tip`·`data-filter` 같은 속성 원문이 가장 정확한 근거**다 |
| docx / xlsx / PDF / PPTX | 문서 추출 MCP(`xberg` 등)로 텍스트 추출 |
| Figma | Figma MCP. 이미 받아둔 스크린샷이 로컬에 있으면 그걸 먼저 본다 (호출 한도 절약) |

여러 자료가 있으면 전부 읽고 통합한다. 기획서에 없고 Figma에만 있는 문구, SB 디스크립션에만 있는
예외 처리가 자주 있다.

**자료 간 날짜를 반드시 확인한다.** 가장 최신 확정본이 판정 기준이다. 오래된 Figma나 구버전 목업을
기준으로 삼으면 멀쩡한 구현을 결함으로 보고하게 된다. 파일명이 비슷한 구버전이 같은 폴더에 있는
경우가 흔하므로 수정 시각을 확인할 것.

### 요건 목록 먼저

케이스를 만들기 전에 **기획 자료의 요건을 전부 목록으로 뽑고 ID(`REQ-01`…)를 붙인다.** 케이스는
이 목록에서 출발한다.

케이스마다 근거를 붙이는 것만으로는 "기획서에 있는데 케이스가 아예 안 만들어진 요건"이 어디에도
드러나지 않는다. 요건 → 케이스 방향으로 표를 만들어야 그 빈칸이 보인다.

- 요건마다 검증 케이스 ID 를 적거나, 검증하지 않을 사유(`exclude`)를 한 줄로 적는다.
  둘 다 없는 요건은 리포트 "요건 커버리지"에 **미검증**(주황)으로 뜨고, 맨 위 할 일 줄에도 나온다.
- 사유는 "화면만으로는 안 됨"처럼 뭉개지 않는다. 아래 "리포트 전 재검토"를 거친 뒤에만 남긴다.
- 스펙에는 최상위 `requirements` 와 케이스의 `req` 로 옮긴다 (`spec_schema.md` "요건 커버리지").

### 케이스 도출

- **근거 없는 케이스는 만들지 않는다.** 케이스마다 원본 위치(`파일명 > 섹션`)와 요건 원문을 붙인다.
  카테고리를 채우려고 "로딩 속도 확인" 같은 일반론을 넣지 않는다.
- **화면에서 눈으로 확인 가능한 것만.** "유지보수성 개선" 같은 목적 서술은 제외한다.

아래 유형을 우선 훑는다. 기획서에서 가장 자주 누락·오구현되는 지점이다.

| 유형 | 무엇을 찾나 |
|---|---|
| 고정 수치 | px 사이즈, 최대 개수, 글자수 제한 → 경계값 ±1 |
| 알럿·문구 | 기획서 문구와 **토씨까지** 일치하는지 |
| 조건부 노출 | "~인 경우에만" → 노출 O 케이스와 X 케이스 둘 다 |
| 토글·상태 전환 | 기본값, 전환 시 동작, 되돌렸을 때 동작 |
| 순서 | 등록 순서대로 노출되는지, 순서변경이 동작하는지 |
| **연속 사용 흐름** | 새로고침 없이 A→B로 이어서 조작했을 때. 아래 참고 |
| **삭제·통합 지시** | "A는 B에 포함시킨다", "C 컬럼은 뺀다" → **없어야 할 것이 없는지**가 핵심 |
| 범위 제외 | "이번 범위 아님"으로 명시된 것이 화면에 없는지 |
| **데이터 상태** | 영역마다 0건(숨김·빈 상자) · 1건 · 많음(최대 개수·"외 N") · 긴 텍스트(말줄임) |
| **입력 오류** | 필수값 누락 · 형식 오류 · 글자수 초과 때 알럿·안내 문구. 정상 입력만 보지 않는다 |
| **로그인 상태별** | 비회원 · 회원 · 어드민에서 노출·동작이 갈리는 요건은 상태마다 케이스 (`session`) |
| **공통 영역** | 우측 레일·헤더처럼 여러 화면에 걸친 요소는 기획서가 "메인"만 적어도 서브 페이지와 좁은 화면(`viewport`)까지 |
| **위치·크기** | 위치 요건은 절대 좌표가 아니라 기준 요소와의 관계("배너 아래", "검색창 오른쪽")로 판정 (`expect_box`) |

"삭제·통합 지시"와 "범위 제외"가 특히 중요하다. 기획 변경은 "추가"보다 "통합·삭제" 지시가
누락되기 쉽고, 그런 건 화면만 봐서는 잘 안 보인다.

**데이터 상태**는 기획서에 0건·많음이 따로 안 적혀 있어도 요건의 일부로 본다. 정상 1건만 보면
"없을 때 빈 상자가 남음", "많을 때 레이아웃 깨짐"이 운영에서야 드러난다. 운영 데이터에 그 상태가
없으면 `precondition` 으로 걸어 두고(없으면 조건 미충족으로 빠짐), 리포트에서 확인한다.

**연속 사용 흐름** — 사용자는 중간에 새로고침하지 않는다. 매번 새로고침 후 한 번만 누르는
케이스만 있으면, 이전 상태가 안 지워지거나 건수가 재계산되지 않는 종류의 버그는 영원히 안 걸린다.

- 먼저 그 요소가 **교체식(단일선택)인지 누적식(다중선택)인지** 확인한다. 기대값이 정반대다.
  교체식은 A→B 후 **B만**, 누적식은 **A∪B** 가 남아야 한다.
- 해당 케이스에 `chains: true` 를 준다. 실패했을 때 러너가 단독 재현으로
  "이어서 해서 깨진 건지 원래 깨진 건지"를 가려 사유에 적어준다.
- **흐름을 길게 늘이지 않는다.** 스텝이 하나 깨지면 그 케이스는 거기서 끝나고 뒤 스텝은
  실행되지 않는다. 열 개를 한 케이스에 몰면 두 번째에서 깨졌을 때 나머지 여덟 개가 정상인지
  알 수 없다. 2~3동작 단위로 끊는다.
- 규격·문구처럼 상태와 무관한 검증은 **단건 케이스로 둔다.** 흐름으로 묶을 이유가 없다.

### 쓰기 판정

각 케이스가 서버에 데이터를 쓰는지 표시한다. 저장·등록·삭제·수정·승인·처리 버튼을 누르면 쓰기다.

"승인"이라는 말을 두 가지로 나눠 쓴다. 섞으면 "승인했는데 왜 안 돌아" 가 된다.

- **케이스 검토 확인**: 사용자가 케이스 MD 를 보고 "이대로 2단계 가자" 고 하는 것
- **쓰기 승인**: 운영 데이터에 쓰는 케이스를 실제로 실행해도 된다는 것. 케이스마다 따로

**쓰기 승인은 대신 판단하지 말고 `쓰기 승인: ☐` 로 두고 넘긴다.** 사용자가 ☑ 로 바꾼 케이스만
2단계에서 `approved: true` 가 된다. 쓰기 케이스에는 정리(cleanup) 절차를 반드시 같이 설계한다
— 없으면 러너가 실행을 거부한다.

### 산출

`<기획_폴더>/qa_auto/cases/{프로젝트명}.md` 에 맨 앞에 **요건 목록 표**(ID · 요건 · 근거 · 케이스 ID 또는
제외 사유)를 두고, 그 아래 케이스별로 요건 ID·요건·근거·분류·심각도·쓰기여부·쓰기 승인·절차·기대결과·정리를 적는다.

작성 후 **사람에게 케이스 검토 확인을 요청하고 멈춘다.** 확인 없이 2단계로 넘어가지 않는다.

## 2단계 — 셀렉터 매핑

1. Playwright로 대상 페이지에 접속한다. **운영 화면을 Playwright 로 직접 열 때는 러너의 `guarded_page` 헬퍼로만
   연다.** 스펙의 세션(auth · cookies · UA)으로 열고, 러너 실행과 같은 안전망(쓰기 요청 차단 · 확인창 취소 ·
   blocklist 주소 차단 · blocklist 글자 버튼 클릭 차단)을 건 페이지를 준다. 결과 폴더는 만들지 않는다.
   ```python
   import sys; sys.path.insert(0, r"$SKILL/qa_auto")
   from qa_run import guarded_page
   with guarded_page(r"<기획_폴더>/qa_auto/specs/{프로젝트명}.json") as page:   # session="guest" 로 세션 선택
       page.goto("https://...")
   ```
   스펙을 아직 안 만들었으면 `meta`(project · base_url · auth)만 든 스펙을 먼저 쓴다. 헬퍼도 blocklist 에 없는
   GET 쓰기와 웹소켓은 막지 못하므로, 누르기 전에 `href` · `onclick` 을 먼저 읽는다.
2. 각 케이스의 절차를 실제로 밟아보며 **DOM 셀렉터를 확인한다. 추측으로 쓰지 않는다.**
3. 이때 **쓰기 액션은 실행하지 않는다.** 셀렉터만 읽고 지나간다.
4. `$SKILL/qa_auto/spec_schema.md` 포맷에 맞춰 `<기획_폴더>/qa_auto/specs/{프로젝트명}.json` 을 쓴다.

### 지킬 것

- `approved` 는 1단계 MD 에서 사용자가 **쓰기 승인 ☑ 한 케이스만 `true`**, 나머지는 `false` 로 둔다.
- **쓰기 스텝이 있는 케이스는 반드시 `writes: true`** 다. 선언 없이 쓰기 스텝(fill · check · 저장 클릭
  등)이 있으면 러너가 케이스를 `BLOCKED`("쓰기 선언 누락") 로 막는다. 클릭은 누르기 직전 화면 글자로도
  다시 본다 (`#approve` 처럼 셀렉터에 글자가 없어도 버튼 글자가 "승인" 이면 쓰기).
- **조회용 입력 · 버튼에는 `"write": false` 를 붙인다.** 검색어 입력, 알림·안내 모달의 확인(닫기만 함),
  "발송 내역" 탭처럼 글자에 쓰기 힌트가 들어 있지만 서버에 쓰지 않는 스텝이다. 이 판단은 Claude 가 2단계에서
  한다. 무엇을 확정하는 모달의 확인, onclick이 함수 호출뿐인 버튼에는 write:false 금지. 붙이기 전에 그 요소의 `href` · `onclick` · 속한 `form` 의 `action` · `method` 를 확인한다. 주소에
  delete · save · toggle · cancel · proc 같은 쓰기 동사가 있으면 GET 쓰기일 수 있으니 `write:false` 를 붙이지
  않고, 그 주소 패턴을 `blocklist` 에 적는다. **네트워크 안전망은 POST · PUT · DELETE 만 막는다.** GET 으로
  보내는 쓰기(레거시 `delete.php?id=`, 링크 · 이미지로 보내는 토글)와 웹소켓은 막지 못한다. 러너는 조작
  스텝(클릭 · 키 입력 · 입력 · 선택 · 다운로드 등)이 시작된 뒤 다음 `goto` 전까지 나간 GET 중 쓰기 동사가 든
  주소를 다른 사이트로 간 것까지 리포트에 "GET 쓰기 의심" 으로 남긴다 (분석 도구 · `ignore_requests` 는 뺌).
- **조회를 POST 로 보내는 화면**(레거시 어드민 목록 · 검색)은 `meta.allow_post` 에 그 **경로 전체**를 적는다
  (`"/admin/order/list.do"`). 쿼리는 빼고, 여러 개를 한 번에 열려면 `"re:/admin/goods/(list|search)\\.do"`
  처럼 `re:` 정규식(경로 전체와 맞아야 함)으로 들어올 값을 정해 적는다. POST 에만 적용되고 PUT · DELETE 는
  열리지 않는다. 경로만 적은 항목은 검수 사이트(같은 도메인)의 요청에만 적용된다. 다른 호스트(외부 API)는
  `"//api.example.com/front/boot"` · `"re://api.example.com/front/(a|b)"` 처럼 호스트를 붙여 적고, 그 호스트에만
  적용된다. `/` 단독 · 4글자 미만 · 쿼리, 경계 없는 `.*` · `.+` 반복, 앞부분 뒤에 `save` · `/delete.do` 같은
  쓰기 주소가 붙어도 맞는 넓은 정규식(`re:/admin/[^/]+` 등)은 실행 전에 멈춘다. 저장 · 삭제 주소는 절대 넣지
  않는다. `?pn=` 처럼 모든 화면이 같이 쓰는 공용 진입점이면 allow_post 로 풀지 말고 사용자에게 알린다.
- **로그 · 통계처럼 화면과 무관하게 나가는 POST** 는 `meta.ignore_requests` 에 경로를 적는다 (형식은
  `allow_post` 와 같고, 다른 호스트의 수집기는 `"//collect.example.com/"` 처럼 경로 `/` 까지 적을 수 있다). 막는
  건 그대로 하고(운영 통계 오염 방지) 판정에만 쓰지 않는다. 구글 애널리틱스 · Clarity 같은 분석 도구는 러너가
  이미 이렇게 처리한다. 상담 채팅 위젯처럼 화면을 그리는 외부 서비스는 여기 넣지 않는다 (막혀서 화면이
  달라졌는데 판정에서 빠지면 그 뒤 실패가 결함으로 넘어간다).
- **첫 dry-run 뒤 막힌 요청을 분류한다.** 리포트에서 "서버 요청을 막음" 이 난 케이스마다 막힌 주소를 보고
  셋 중 하나로 정한다: 조회 POST → `allow_post`, 로그 · 통계 → `ignore_requests`, 실제 쓰기 → 그 스텝을
  쓰기로 두고 케이스를 쓰기 케이스로 바꾸거나 빼서 사용자에게 알린다. 분류를 모르겠으면 사용자에게 묻는다.
  사유가 "write:false 로 둔 버튼이 서버 요청을 보냄" 이면 그 버튼과 케이스부터 본다. 조회 버튼이면
  `allow_post` 에 그 경로를 적는다. **빈 폼 · 잘못된 입력 검증 케이스에서 막힌 요청이면 검증 누락 후보로
  기록한다 (allow_post 에 넣지 않는다).** 사용자에게 결함 후보로 알린다.
- **로그인 상태가 다른 화면(비회원 · 회원 · 어드민)도 스펙 하나로 쓴다.** 스펙을 나누면 리포트와
  웍스 로그가 따로 나와 같은 결함이 두 번 실린다. `meta.sessions` 에 세션을 두고 케이스에
  `session` 을 준다 (`spec_schema.md` "세션 여러 개"). 프론트와 어드민을 한 세션으로 오가면
  `login_check` 를 `when_url` 로 나눈다.
- **케이스마다 `area`·`fix` 를 적는다.** 검수 결과는 기획팀이 웍스에 글로 올려 넘기는데,
  `fix` 가 그 글의 한 줄이 된다. 형식은 **`대상 오류: 현재 현상 (SB: 기준)`** 이다.
  예: `품절예상 판정 오류: 재고가 아닌 12주 판매량으로 판정 중 (SB: 현재고 ≤ 3개월 평균 × 20%)`.
  `~변경`·`~추가` 로 쓰면 기획 변경(신규 요청)으로 읽혀 결함으로 처리되지 않고, `~해주세요` 로 쓰면
  제안으로 읽힌다. "변경"은 진짜 기획 변경일 때만 쓴다. 근거가 SB 가 아니면 그 자료 이름을 쓴다
  (`기획서: …`). 현재 현상 자리에 `{actual}` 을 쓰면 실행 때 실제 값으로 바뀐다 (개발팀이 일부만 고쳐
  현상이 바뀌어도 로그가 맞게 나온다). `area` 가 없는 항목은 웍스 로그에서 "- 기타" 아래로 간다.
- **케이스마다 `req` 로 요건 ID 를 단다.** 1단계 요건 목록과 이어져야 리포트의 요건 커버리지가 맞는다.
- **`severity` 를 단다** (`치명` · `주요` · `경미`). 같은 영역 안에서 전달 순서가 이 순서를 따르고,
  `치명` 은 웍스 로그 줄 앞에 `[치명]` 이 붙는다. 결제·주문·금액·노출 누락처럼 업무가 막히는 것과,
  비회원에게 전문의약품 정보 · 가격이 보이거나 면허 · 회원 등급 확인이 빠진 것처럼 노출 대상이 어긋난
  것만 `치명`. 이 분류는 검수 우선순위일 뿐 규제 판단이 아니다. 규제 해당 여부는 법무 · 규제팀이 본다.
- **허용값이 아닌 `kind` · `severity`, `source` 가 빈 `defect` 는 실행 전에 멈춘다.** 오타 하나로
  엉뚱한 건이 개발팀에 가는 걸 막기 위함이다.
- **"없어야 함" 판정에는 `anchor` 를 단다.** `expect_hidden`, `expect_count` 의 `count: 0` · `max`,
  `expect_text` 의 `not_contains` 는 셀렉터가 틀리거나 화면이 덜 그려져도 통과해 버린다. `anchor` 에
  "이 영역이 다 그려졌다" 를 보여 주는 요소(표 헤더, 패널 제목)를 주면 러너가 그게 보일 때까지 기다린 뒤
  판정한다. 러너는 없어질 때까지 기다린 뒤(`settle`, 기본 5초) **관찰 구간(`hold`, 기본 1.5초) 내내**
  없어야 통과로 보고, 끝나고 anchor 가 아직 있는지 다시 본다. 늦게 그려지는 금지 문구는 실패, 필터 뒤
  늦게 빠지는 행은 통과가 된다. anchor 없이 요소가 0개면 판정 불가(`ERROR`) 다. 케이스에 `anchor` 를
  주면 그 케이스의 모든 스텝에 적용된다. `expect_visible` 도 anchor 가 보이는데 요소가 없으면
  `FAIL`(미노출 결함), anchor 도 안 보이면 `ERROR`(셀렉터 · 로딩 문제)로 가른다.
  **부재 판정용 anchor 는 그 스텝에 단다(step anchor).** 케이스 단위 anchor 는 모든 스텝이 같은 영역을 볼 때만
  쓴다. 넓은 anchor 는 셀렉터가 낡은 "요소 없음" 을 미노출 결함(FAIL)으로 바꾼다. `body` · `html` · `:root` 는
  러너가 anchor 없음으로 치고, `header` · `#wrap` · `#container` · `#content` 류는 스펙 점검 경고가 뜬다.
- **운영 데이터에 기대는 케이스는 `precondition` 을 건다.** 특정 코드의 행, "품절 상품이 있을 때" 같은
  전제는 데이터가 바뀌면 사라진다. 그 확인 스텝에 `"precondition": true` 와 `anchor` 를 주면, anchor 는
  보이는데 전제가 안 맞을 때 FAIL 이 아니라 **조건 미충족(NA)** 으로 빠진다. anchor 가 없거나 안 보이면,
  또는 안전망이 요청을 막았거나 확인창을 취소한 뒤면 점검 필요다. precondition 은 **검증 대상과 다른 경로로 확인**한다 (검증할 배너가 안 보이는 걸
  "배너 데이터 없음" 으로 읽으면 미노출 결함이 NA 로 숨는다). 같은 케이스가 3회 연속 NA 면 경고가 뜬다.
- **알럿 · 안내 문구는 `equals`** (완전일치)로 쓴다. 화면 문구는 `expect_text`, 브라우저 알럿 · 확인창은
  `expect_dialog` 에 쓴다. `contains` 는 부분일치라 토씨 차이를 놓친다. 형식만 볼 땐 `matches`(정규식),
  표의 모든 행을 볼 땐 `all: true`. 승인 안 된 스텝에서 뜬 확인창은 취소되므로, `expect_dialog` 로 문구를
  확인한 뒤의 판정은 실제 흐름(확인을 누름)과 달라 어긋나도 점검 필요가 된다. 확인창 문구 확인은 케이스의
  마지막 판정으로 둔다.
- **문구 여러 개를 한 화면에서 확인할 땐 `soft`** 를 준다. 첫 불일치에서 멈추지 않고 나머지까지 본 뒤
  한꺼번에 실패 처리한다. 흐름(앞 스텝이 뒤 스텝의 전제)에는 쓰지 않는다.
- **크기·위치 요건은 `expect_box`** 로 쓴다. `expect_js` 로 좌표를 직접 계산하지 않는다.
- **쓰기 케이스가 있으면 `meta.residue_check`** 를 넣는다. 실행 끝에 `{QA_PREFIX}` 로 검색해 테스트
  데이터가 남았는지 본다. cleanup 이 예외 없이 끝났다고 실제로 지워졌다는 보장은 없다.
  지난 실행이 남긴 데이터와 섞이지 않게 입력값에 `{RUN_ID}`(실행 번호)를 붙여도 된다.
- **승인 쓰기 케이스는 첫 스텝을 `goto` 로 한다.** 러너는 그 goto 가 끝난 뒤부터 cleanup 까지만, 지금
  페이지에서 나간 쓰기 요청을 통과시킨다. 앞 케이스가 남긴 타이머 · 팝업 · 다른 세션 탭의 요청이 쓰기 허용
  구간에 섞이지 않게 하기 위함이다. goto 로 시작하지 않으면 `BLOCKED` 다.
- **스펙에 `meta.runner_min: 5` 를 적는다** (현재 러너 버전 5). 러너 5 이상에서 확인한다. 4 이하는 bat의
  버전 확인이 막으므로 예전 bat은 지우고 --init으로 새로 만든다.
- **케이스마다 `kind` 를 정한다.** 기획팀이 리포트를 먼저 보고 개발팀에 넘길 것만 추리는데,
  그 선을 여기서 긋는다. `defect`(확정 기획서 근거 있음, 기본값) / `improve`(사용성 제안) /
  `gap`(기획서에 정의 없음). `source` 에 확정 자료 위치를 못 적겠으면 `defect` 가 아니다.
- 한글 버튼은 `label` 필드에 버튼 텍스트를 넣는다 — 스펙 단계의 쓰기 판정과 재현 절차가 이 값을 쓴다.
- `blocklist` 에 절대 눌리면 안 되는 버튼을 넣는다. 승인 여부와 무관하게 막힌다.
  `text=발송` 은 버튼 글자가 정확히 "발송" 일 때만, `text*=발송` 은 "알림톡 발송" · "SMS 발송하기" 처럼
  그 말이 들어 있기만 해도 막는다. 읽기 케이스에서는 `text=` 를 주로 쓴다 ("발송 내역" 탭을 눌러야 하는
  경우가 많다). 글자가 아닌 패턴(`sendSms` 같은 함수명 · `withdraw` 같은 주소 일부)은 셀렉터 · 주소 · 입력값 ·
  js 에 있으면 실행 전에 막고, **실행 중 나가는 요청 주소에 있어도 메서드와 무관하게 네트워크 단에서**
  막는다 (스크립트 · 스타일 · 글꼴 파일 요청은 대조하지 않음). GET 쓰기 주소는 여기에 적는다. 글자가 아닌
  패턴은 5글자 이상으로 적는다. `send` · `del` 처럼 짧으면 엉뚱한 요청까지 막혀 점검 필요가 늘어나므로 스펙
  점검 경고가 뜬다. 버튼 글자를 막으려는 것이면 `text=` 로 적는다.
- **승인된 운영 쓰기 케이스에는 러너가 내장 blocklist 발송·결제·발주·일괄삭제(띄어쓴 '일괄 삭제' 포함)를
  `text*=` 로 항상 더한다.** 승인 케이스에서는 쓰기 힌트와 네트워크 안전망이 꺼지므로 마지막 보호다. 정말 그 버튼을 눌러야
  하는 스펙만 `meta.blocklist_off` 에 그 항목을 그대로 적어 풀고, 사용자에게 알린다. 접두어 없이 `"발주"` 로
  적어도 `text*=발주` 로 받고, 일괄삭제를 풀면 띄어쓴 `일괄 삭제` 도 같이 풀린다. 내장 목록에 없는 항목(오타)은
  스펙 점검 경고만 남기고 무시한다 (그 버튼은 계속 막힌다).
- **순서·계산 판정은 `expect_js` 를 쓴다.** CSS 인접 선택자(`+`)는 DOM 형제만 보므로, 필터로 숨긴
  행을 건너뛴 "화면에 보이는 순서"를 검사하지 못해 **거짓 통과**가 난다. 자동화에서 가장 위험한
  실패는 실패를 놓치는 게 아니라 통과라고 잘못 보고하는 것이다. expect_js 는 값만 읽는다. 평가 뒤
  0.2초까지 나간 요청은 막지만, 그보다 늦게 나가는 `setTimeout` 요청은 막지 못하므로 타이머를 쓰지 않는다.
- 툴팁이 `title` 속성이 아니라 JS로 생성되는 경우가 많다. `hover` 액션으로 띄운 뒤 실제 툴팁
  요소를 `expect_text` 로 검사한다.
- **결함 증빙 스크린샷은 문제 지점만 찍지 않는다.** `screenshot` 에 `selector` 와 `context` 를 주어
  주변 정상 행·헤더가 같이 담기게 한다. 전체 화면 한 장으로는 수백 행 중 어디가 문제인지 아무도
  못 찾는다.
- 인라인 편집은 `dblclick` → `type` → `press Enter` 로 밟는다. `fill` 은 더블클릭 이후에 생기는
  input 을 못 잡는다.
- 엑셀 내보내기는 `download` + `expect_file` 로 검증한다. 기대 행수는 `row_count_js` 로 화면에서
  읽어 비교한다 — 운영 데이터는 계속 바뀌므로 고정값을 박을 수 없다.

### 검증

```
py "$SKILL/qa_auto/qa_run.py" qa_auto/specs/{프로젝트명}.json --dry-run
```

**점검 필요(ERROR) 0건이 되면 넘긴다.** 점검 필요는 셀렉터 · 대기 · `write:false` · `allow_post` 문제이므로
고치고 다시 돌린다. 실패(FAIL)는 결함 후보이므로 사용자에게 보고하고, **기대값을 고쳐 통과시키지 않는다.**
차단(BLOCKED)은 사유를 보고 쓰기 선언 · `write:false` 를 바로잡는다.

## 3단계 — 실행·리포트

```
py "$SKILL/qa_auto/qa_run.py" qa_auto/specs/{프로젝트명}.json
```

운영 데이터에 쓰는 케이스(승인된 쓰기 케이스)는 **담당 기획자가 Claude 로 실행한다.** 팀원은
`qa_auto/run_qa.bat` 더블클릭으로 읽기만 돌린다 (1번 읽기만 · 2번 지난 실행에서 실패한 것만 다시).
bat 에는 쓰기 실행 메뉴가 없다. 스펙에 `approved: true` 가 영구히 남아 있어서, 메뉴가 있으면 승인자가
아닌 사람이 Y 한 번으로 운영에 쓰게 된다. 예전에 만든 bat 은 `--init` 을 한 번 더 돌려 새로 만든다.

리포트는 `qa_auto/output/{프로젝트}_{일시}/` 에 생기고, bat 은 이번 실행 리포트를 기본 브라우저로 연다.
스크린샷은 클릭하면 확대되고 `원본 크기` 버튼으로 1:1 확인이 된다.

러너가 알아서 하는 것:

- **실패하면 한 번 더 돌린다.** 1차 실패(FAIL) 뒤 재실행에서 통과하면 통과로 덮지 않고 **불안정**으로
  둔다. 개발 전달과 요건 통과에서 빠지고 기획팀이 보고 판단한다 (첫 전달에서 "재현 안 됨" 이 나오면
  이후 전달 전체가 의심받는다). 1차 스크린샷은 `_try1` 로 남는다. 점검 필요(ERROR) 뒤 통과는 통과로 두고
  "재실행 통과" 표시만 단다. 1차 실패 뒤 재실행이 점검 필요면 점검 필요로 두고 사유 앞에 "1차 실패: …" 를
  남긴다. 쓰기 케이스는 재실행하지 않는다. 같은 셀렉터가 여러 케이스에서 시간 초과면
  화면 구조가 바뀐 것이라 재실행을 생략하고 "셀렉터 갱신 요청" 을 띄운다. 끄려면 `--no-retry`.
- **막은 뒤의 실패는 개발팀에 넘기지 않는다.** 안전망이 요청을 막았거나 확인창을 취소한 케이스에서 판정이
  어긋나면, 화면 흐름이 실제 사용과 달라진 것이라 실패(FAIL)가 아니라 점검 필요(ERROR)로 둔다. 사유는
  "판정 불가 - 안전망 개입(요청 차단 · 확인창 취소)으로 화면 흐름이 실제와 다름. 막은 요청: … · 이후 결과: …"
  다. 다른 사이트로 가는 요청이 막혀도, 케이스가 연 팝업의 쓰기 요청이
  막혀도, 취소한 확인창의 문구를 `expect_dialog` 로 확인한 뒤여도 같다.
- **판정 못 한 건이 있으면 "오류 없음" 이라고 쓰지 않는다.** 점검 필요 · 불안정 · 조건 미충족 · 차단이 있으면
  웍스 로그 · md · 개발 탭이 "판정한 M건 중 기획 미반영 오류 N건" 과 "판정하지 못한 K건은 기획팀 확인 뒤 다시
  (추가로) 전달합니다." 로 나간다. 승인 대기는 따로 센다.
- **지난 실행과 비교한다.** 같은 스펙의 마지막 **전체** 실행과 비교한다 (쓰기 케이스가 있는 스펙은 같은
  모드끼리). 실패가 이어지면 "계속 실패", 통과 · 점검 필요 · 새 케이스에서 실패가 되면 "새로 실패",
  판정까지 가다가 못 가게 되면 "판정 불가로 바뀜", 점검 필요가 이어지면 "계속 점검 필요" 다. 일부만 돌린
  실행이나 중간에 멈춘 실행은 기준이 되지 않는다. 기준을 바꾸려면 `--compare <결과폴더>`.
  러너를 업데이트한 직후 예전에 통과하던 케이스가 "판정 불가로 바뀜" 이 되는 건 판정 기준이 엄격해진
  것이지(anchor 없는 부재 판정 등) 회귀가 아니다. 사용자에게 그렇게 알리고 스펙을 고친다.
- **실패 케이스의 동작 기록(trace)을 남긴다.** 기획팀 검토 탭에만 링크가 있다. **개발팀에 넘기지 않는다**
  — 운영 어드민 세션 쿠키와 거래처 화면이 그대로 들어 있다. 개발팀이 요청하면
  `py "$SKILL/qa_auto/qa_run.py" --strip-trace <trace.zip>` 으로 만든 사본만 넘긴다. 사본은 쿠키 · 로그인
  상태, 인증 · 토큰 · 세션 헤더 값, 주소의 쿼리 값(fragment 포함), 요청 본문, JSON · XML · 비동기 응답 본문을
  지운다. **화면 스냅샷 안의
  입력값 · 숨은 토큰, 화면에 보이는 운영 데이터, 파일 내려받기 · 바이너리 응답 본문(엑셀 · CSV 등)은 남는다**고 함께 알리고, 넘기기 전에 QA 계정에서
  로그아웃해 세션을 끊는다. 끄려면 `--no-trace`.
- **콘솔 · 네트워크 오류를 모은다.** JS 오류, 콘솔 에러, 4xx·5xx 응답, 새 창(팝업) 열림, 웹소켓 연결을
  케이스별로 참고로만 싣는다. 기획서 근거가 아니므로 판정과 개발 전달에는 넣지 않는다.
- **실행이 중간에 멈춰도 결과를 남긴다** (세션 만료 · 브라우저 오류 등). 진행 중이던 쓰기 케이스의 정리를
  먼저 시도하고, 그때까지 결과로 리포트를 만든다. 맨 위에 "N번째 케이스에서 멈춤" 과 정리되지 않은 쓰기
  케이스(입력값 포함)가 뜬다. **중단된 실행은 개발팀에 전달하지 않는다** — 개발 탭 · 웍스 로그 · md 가
  "검수 중단 · 전달 보류 (N건 중 M건 실행)" 으로 나오고 복사 버튼이 없다. 종료 코드는 3 이다.
  세션 만료 안내에 "직전에 막은 요청" 이 같이 뜨면 다시 로그인시키기 전에 그 요청부터 분류한다 (로그인 유지
  요청을 안전망이 막아 사이트가 스스로 로그아웃했으면 다시 로그인해도 같은 결과다).
- **cleanup 만 실패해도** 할 일 맨 앞에 "운영 데이터 미정리 N건" 이 뜨고, 케이스에 그때 입력한 값이 나온다.
  사용자에게 바로 알리고 그 값으로 운영 데이터를 찾아 지우게 한다.
- **내려받은 엑셀은 판정이 끝나면 지운다** (실패한 경우만 증빙으로 남김). 지난 실행 폴더는 "모르면
  남긴다" 원칙으로 정리한다: 최근 10회(`meta.keep_runs`), 스펙 · 모드별 마지막 비교 기준, 예전 형식 실행,
  운영 데이터 미정리가 있는 실행, 사람이 넣은 파일(캡처 PPT 등)이 있는 폴더는 남긴다. 개발 전달 항목이
  있던 실행은 리포트 · 동작 기록을 남기고 내려받은 파일만 지운다. 한 번에 3개 폴더까지만 지운다 (내려받은 파일
  폴더도 같이 센다).
- 리포트 맨 위에 **할 일 한 줄**(운영 데이터 미정리 · 개발 전달 · GET 쓰기 의심 · fix 없음 · 점검 필요 ·
  불안정 · 미검증 요건 등)이 있고, 케이스는 영역별로 묶여 할 일이 위로 오게 정렬된다 (영역도 가장 심한
  상태 순). 통과는 영역마다 "통과 N건" 으로 접힌다. 스펙 점검 경고(fix · area · anchor 누락)는 종류별
  한 줄로 묶여 회색으로(줄 끝 괄호에 판정 · 전달에 생기는 차이), 운영 위험 경고는 주황으로 뜬다. GET 쓰기
  의심은 케이스 머리줄 태그와 주황 경고 목록(케이스 · 주소 한 줄씩)에 뜨고, 콘솔 끝에도 한 줄 찍힌다.
  중단된 실행은 할 일 맨 앞이 "다시 실행 필요"(세션 만료면 "다시 로그인 후 실행")이고 개발 탭 숫자는 "보류" 다.

### 재검수 (개발팀이 고친 뒤)

```
py "$SKILL/qa_auto/qa_run.py" qa_auto/specs/{프로젝트명}.json --rerun-failed latest
```

같은 스펙의 마지막 전체 실행에서 실패 · 점검 필요 · 불안정이었던 케이스만 다시 돌리고, 그 실행과
비교해 수정됨 · 계속 실패를 표시한다. 특정 결과 폴더를 기준으로 하려면 `latest` 대신 폴더 경로를 준다.
개발팀 회신은 웍스 로그 줄 끝의 케이스 ID 로 온다 (`… · TC-012`). 회차마다 번호가 다시 매겨지므로
번호가 아니라 ID 로 골라 돌린다: `--case TC-003,TC-007`.

재검수에서 통과했다고 끝내지 않는다. 고친 부분 주변이 깨지는 경우가 흔하므로, 마지막에는
전체를 한 번 돌려 "새로 실패"가 없는지 본다.

| 파일 | 누가 보나 |
|---|---|
| `리포트.html` 의 **기획팀 검토** 탭 | 전체 케이스. 통과는 접혀 있고 눌러서 펼친다 |
| `리포트.html` 의 **개발 전달용** 탭 | 웍스에 올릴 로그 + 항목별 근거. `복사` 버튼 있음 |
| `웍스등록.txt` | 위 로그와 같은 내용. 웍스에 그대로 붙여넣는 용도. 줄 끝에 케이스 ID |
| `개발전달.md` | 근거·재현 절차(입력값 포함)·실패 시점 주소(토큰 가림)·실행 환경·첨부할 스크린샷 이름까지 담은 상세본. 동작 기록은 없음. 스크린샷은 파일을 따로 첨부한다 |

`fix` 가 없는 결함은 판정 메시지에 기대 · 실제가 있으면 `{area} 오류: '{실제}' 노출 (SB: '{기대}')`, 크기 · 위치처럼
`실제 (기대 값)` 이면 `{area} 오류: '{실제}' (SB: '{값}')`, 둘 다 없으면 `{area} 오류: {현상 앞 40자}… (SB: {source})` 로 나간다 (`area` 가 없으면 '화면'. 테스트 제목 · 셀렉터는 안 씀).
할 일에 "이번 전달 중 fix 없음 N건" 이 뜬다. 넘기기 전에 스펙에 `fix` 를 채운다.

로그는 **지시문만** 싣는다. 근거·재현 절차는 상세본에 남긴다. 설명이 붙으면 받는 쪽이
"추가 검토 요청"으로 읽어 일이 안 돌아간다.

개발 전달용에는 `improve`·`gap` 이 안 들어간다. 기획 확정이 안 끝난 항목까지 같이 넘기면
근거가 확실한 결함까지 같이 흐려지기 때문이다. 대신 "전달에서 뺀 항목" 으로 목록만 보여준다.

### 케이스 상태

| 상태 | 뜻 | 조치 |
|---|---|---|
| `PASS` | 기획서대로 구현됨 | - |
| `FAIL` | 화면을 확인했고 기획서와 다름 | `kind` 에 따라 개발 전달 / 기획팀 보류 |
| `ERROR` 점검 필요 | 판정까지 못 감 (요소 없음 · 시간 초과 · 서버 요청 차단 · 확인창 취소 · 막은 뒤 판정 어긋남 · 정리(cleanup) 실패) | 스크린샷·동작 기록으로 원인 확인. 셀렉터 · anchor · `write:false` · `allow_post` · `ignore_requests` 문제면 스펙 수정 |
| `FLAKY` 불안정 | 1차 실패, 재실행 통과 | 기획팀이 다시 돌려 보고 판단. 반복되면 결함으로 전달 |
| `NA` 조건 미충족 | `precondition` 이 안 맞음 (anchor 는 보임) | 데이터가 생기면 다시 실행하거나 다른 대상 데이터로 스펙 수정 |
| `SKIPPED` 승인 대기 | 쓰기 미승인 · 읽기만 실행 | 사용자 쓰기 승인 후 Claude 가 실행 |
| `BLOCKED` 차단 | blocklist · cleanup 누락 · 쓰기 선언 누락 · 버튼 글자가 쓰기 | 사유대로 스펙 수정 |

개발 전달에는 `FAIL` 이면서 `kind: defect` 인 것만 간다. `ERROR` 는 셀렉터가 낡아서 난 실패일 수
있으므로 개발팀에 넘기지 않는다. 요소가 아예 없는 게 결함이면 케이스에 `anchor` 를 줘서 "페이지는 정상인데
그 요소만 없다" 를 증명해야 `FAIL` 로 잡힌다.

## 기획 변경 시 (SB 버전 올림)

1. 새 자료와 스펙의 `requirements` 를 대조해 **바뀐 · 추가된 · 빠진 요건을 먼저 표로 보여 준다.**
2. 영향받는 케이스만 고친다. 안 바뀐 케이스는 건드리지 않는다 (지난 실행 비교가 끊긴다).
3. **케이스 ID 는 재사용하지 않는다.** 빠진 케이스의 ID 는 비워 두고 새 케이스는 새 번호를 쓴다. 지난 실행
   비교가 ID 로 맞춰지므로, 번호를 다시 매기면 다른 케이스끼리 비교된다.
4. 기준은 스펙 JSON 이다. 케이스 MD 는 검토용으로 같이 고친다.

## 리포트 전 — "화면만으로는 안 됨" 재검토

리포트를 내기 전에, 검증을 포기하고 빼둔 항목을 **반드시 한 번 더 훑는다.**

처음 분류할 때는 보통 (1) 로그인 세션이 없고 (2) 원천 데이터를 가진 다른 화면을 아직 안 봤다.
그 시점의 "못 한다"는 판단이 그대로 굳어서 **검수 범위가 통째로 빠진다.** 조건이 바뀌었는데
재검토하는 단계가 없으면 아무도 다시 안 본다.

항목마다 아래를 확인한다.

- **파일을 받아서 열면 되는가** — 엑셀·CSV·PDF 다운로드는 Playwright 로 받아 파싱하면
  행수·컬럼·순서까지 화면과 대조된다. "파일 비교라서 불가"는 대개 틀린 판단이다.
- **원천을 가진 다른 화면이 있는가** — 관리자 상세 화면이 URL 파라미터로 단건 조회를 지원하면
  (`?code=12345` 같은) 계산 결과가 아니라 **산식 자체**를 검증할 수 있다. 화면 검수에서 가장
  값어치가 큰 영역이라 빠뜨리면 손해가 크다.
- **시간만 있으면 되는가** — 갱신 주기 같은 건 간격을 두고 스냅샷을 두 번 찍으면 된다.

정말로 안 되는 것만 남긴다. 남길 때는 **왜 안 되는지 한 줄을 적는다.** "개발팀 확인"처럼
뭉개지 않는다 — 그렇게 적으면 다음 사람도 똑같이 건너뛴다.

## 안전장치

운영 서버를 대상으로 하므로 쓰기에 잠금이 걸려 있다. 러너가 강제한다. 막지 못하는 것은 표 마지막 행.

| 장치 | 동작 |
|---|---|
| 쓰기 선언 · 승인 | 쓰기 스텝이 하나라도 있으면 `writes: true` + `approved: true` 여야 실행. 선언 누락은 `BLOCKED`, 미승인은 `SKIPPED` |
| 누르기 직전 판정 | 누를 수 있게 될 때까지 기다린 뒤 버튼의 화면 글자(innerText · value · aria-label · alt · 아이콘 대체 글자)로 blocklist 와 쓰기 힌트를 다시 보고, **읽은 그 요소를** 누른다 ("준비 중" 이 그 사이 "발송" 으로 바뀌는 경쟁 방지). blocklist 는 그 요소를 감싼 버튼 · 링크의 글자까지 보고(버튼 안 아이콘을 누르는 셀렉터), `press` 의 Enter · Space 는 포커스 요소와 속한 폼의 제출 버튼 글자까지 본다. 승인 안 된 케이스에서 쓰기 버튼이면 `BLOCKED` |
| 네트워크 안전망 | 승인된 쓰기 케이스 밖에서는 서버로 가는 쓰기 요청(POST · PUT · DELETE 등)을 아예 보내지 않는다. 막히면 사이트와 무관하게 그 케이스는 `ERROR`. 예외: `meta.allow_post`(조회 POST, 경로 전체일치, 경로만 적으면 검수 사이트에만), `meta.ignore_requests` · 분석 도구(막되 판정 무관) |
| 쓰기 허용 구간 | 승인 쓰기 케이스도 첫 `goto` 뒤부터 cleanup 까지, 지금 페이지에서 나간 요청만 통과. 팝업 · 앞 케이스 · 다른 세션 탭의 요청은 항상 막고, 케이스 시작 때 팝업을 닫는다 |
| 확인창 | "삭제하시겠습니까?" 같은 확인창은 승인된 쓰기 스텝부터 다음 조작 전까지만 수락하고, 나머지는 취소한다 |
| blocklist | 스펙에 적은 버튼 글자 · 주소 패턴은 승인 여부와 무관하게 `BLOCKED`. 주소 패턴은 실행 중 요청도 메서드와 무관하게 막는다. 승인 쓰기 케이스에는 내장 blocklist 발송·결제·발주·일괄삭제(띄어쓴 '일괄 삭제' 포함)를 항상 더한다 (`meta.blocklist_off` 로 항목별 해제) |
| 구버전 러너 | bat 은 러너 버전이 낮으면 실행하지 않고 업데이트를 안내한다 |
| cleanup 강제 | 쓰기 케이스에 정리 절차가 없으면 실행 거부. 테스트가 실패해도 · 세션이 만료돼도 정리는 시도 |
| QA 프리픽스 경고 | 입력값에 `[QA]YYYYMMDD` 가 없으면 리포트에 경고 |
| 잔여 데이터 점검 | 승인된 쓰기 케이스가 돌았으면 마지막에 `meta.residue_check` 실행. 남아 있으면 경고 (읽기 스텝만 허용) |
| 재실행 · 진단 제외 | 쓰기 케이스는 자동 재실행 · 연속 사용 진단을 하지 않음 (운영 데이터 중복 생성 방지) |
| `expect_js` 읽기 전용 | `.click(`·`fetch(` 등 금지 패턴을 거르고, 평가하는 동안은 승인된 케이스여도 서버 쓰기 요청을 막는다 |
| 막지 못하는 것 | blocklist 에 없는 GET 쓰기, 웹소켓, expect_js 의 늦은 타이머 요청. 화면 글자로 못 알아보는 버튼(글자 · alt 없는 배경 이미지 버튼, CSS 로 그린 글자, 다른 요소를 가리키는 이름(aria-labelledby), 폼 밖 입력칸 Enter 로 스크립트가 보내는 요청). GET 쓰기 의심 · 웹소켓 연결은 리포트에 남긴다 |

`--dry-run`(bat 1번) 은 쓰기 케이스를 통째로 건너뛴다. 스펙에 선언이 빠진 쓰기가 있어도 POST · PUT ·
DELETE 요청은 네트워크 안전망이 막는다. **GET 으로 보내는 쓰기는 blocklist 에 주소 패턴을 적은 것만 막힌다.**
그래서 2단계에서 `write:false` 를 붙이기 전에 링크 · 폼 주소를 확인하는 것이 중요하다.

러너를 고친 뒤에는 회귀 테스트를 돌린다 (한 번에 하나씩, 다른 리뷰 · 실행과 동시에 돌리지 않는다):
`py "$SKILL/qa_auto/tests/test_gates.py"`, `py "$SKILL/qa_auto/tests/test_runner.py"` (브라우저 없음),
`py "$SKILL/qa_auto/tests/regress/run_regress.py"` (리뷰에서 재현한 쓰기 우회 · 오탐 경로를 로컬 서버로
확인. 실행마다 임시 폴더 · 빈 포트를 쓰고 끝나면 지운다. 일부만: `--only dry,late`).

> **`approved` 를 임의로 켜지 않는다.** 사용자가 명시적으로 지시한 케이스만 켠다.

## 주의

- 스펙 작성·검증 중에도 저장/등록/삭제 버튼을 누르지 않는다.
- 세션 만료로 로그인 페이지가 뜨면 **즉시 멈추고 로그인 창을 다시 띄운다. Claude 가 로그인 시도를 하지 않는다.**
- 기획서와 구현이 다르면 그게 곧 테스트 실패다. 임의로 기획서 쪽을 맞춰 해석하지 않는다.
- 가상 스크롤(tui-grid 등)을 쓰는 화면은 DOM에 일부 행만 있다. 전수 확인이 필요하면 검색·필터로
  대상을 좁히거나 스크롤을 돌려야 한다. 보이는 행만 보고 "그런 값 없음"이라고 단정하지 말 것.

## 수기 검수 항목 분류

사용자가 직접 검수한 항목 목록을 주면, 각각을 확정 기획서와 대조해 나눈다.

| 분류 | 판단 기준 | 처리 |
|---|---|---|
| **결함** | 확정 기획서에 있는데 구현에 없음 | 회귀 스펙에 케이스 추가 |
| **개선 요청** | 기획서에 근거 없음 | **별도 스펙 파일**로 분리 |
| **재현 안 됨** | 확인했으나 재현 실패 | 조건(화면폭·배율·데이터)을 되물음 |
| **화면만으로는 안 됨** | 화면 밖 경로가 필요 | 아래 재검토를 거친 뒤에만 남김 |

마지막 분류를 **"자동화 불가"라고 부르지 않는다.** 불가능한 게 아니라 **경로가 다를 뿐**인
경우가 대부분이고, 이름을 그렇게 붙이면 검증을 시도조차 안 하게 된다.

개선이 **한두 건**이면 스펙을 나누지 말고 해당 케이스에 `kind: "improve"` (또는 `"gap"`) 만
달아둔다. 리포트가 개발 전달용에서 알아서 빼준다.

**스펙을 분리하는 이유**: 개선 요청은 아직 구현 전이라 전부 실패로 나온다. 회귀 검사와 섞으면
"항상 빨간 리포트"가 되어 진짜 결함이 묻힌다. 분리하면 개선 스펙은 구현 진척 추적용으로,
회귀 스펙은 "전부 통과가 정상"인 상태로 각각 의미를 갖는다.

개발팀에 전달할 때도 결함과 개선을 나눠 보내라고 안내한다. 결함은 근거가 명확해 이견이 적고,
개선은 일정 협의가 필요해 성격이 다르다.
