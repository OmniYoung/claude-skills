# SB(화면설계 스토리보드) 생성 — Figma 소스

컨펌된 Figma 화면 디자인으로부터 개발자용 화면설계 스토리보드(SB, PPTX)를 만든다. 사용자가 Figma 파일/노드 URL(node-id 포함)을 주지 않았으면 먼저 요청한다.

> 전제: 화면 기획은 **① Figma 디자인 → ② 이해관계자 컨펌 → ③ SB(PPTX)** 순서로 진행한다. 이 스킬은 **디자인이 이미 컨펌된 뒤**에 쓴다 — 아직 안 굳었으면 먼저 Figma를 다듬고 컨펌부터 받을 것.
>
> **HTML 목업과의 결정적 차이**: HTML은 Playwright로 실제 hover/click/dblclick을 실행시켜 인터랙션 상태를 만들어낼 수 있지만, Figma는 정적 캔버스라 그렇게 할 수 없다. 호버 툴팁·편집모드·저장완료·빈 상태 같은 인터랙션 상태는 **디자이너가 상태별로 별도 프레임(또는 컴포넌트 variant)을 이미 만들어둔 경우에만** 캡처할 수 있다. 필요한 상태 프레임이 파일에 없으면 상태를 추측·합성하지 말고 컨펌 단계로 돌아가 상태별 프레임을 요청할 것.
>
> 목표는 "개발자가 이 SB만 보고 Figma를 열어보지 않아도 개발 가능한 수준"이다. 툴팁·토스트·안내문 등의 문구는 추측하지 말고 `get_design_context`로 실제 텍스트 레이어 원문을 확인해 그대로 인용한다.

## 준비물

1. **컨펌된 Figma 파일** — 아래 두 조건이 안 갖춰져 있으면 캡처 자체가 불가능하니 먼저 확인한다:
   - 섹션/표/카드가 프레임 단위로 분리돼 있을 것 (컬럼 스펙 슬라이드는 프레임 하나를 통째로 캡처한다)
   - 인터랙션 상태(호버·편집중·저장완료·빈 상태 등)가 상태별로 각각 별도 프레임 또는 컴포넌트 variant로 존재할 것 — 네이밍 규칙이 있으면(`섹션명/상태명` 등) 먼저 물어본다
2. **Figma Desktop 앱**이 해당 파일을 열어둔 상태 + Figma MCP 서버 연결(`get_metadata`/`get_screenshot`/`get_design_context`/`download_assets` 사용 가능해야 함). 연결이 안 돼 있으면 사용자에게 먼저 연결해달라고 안내한다.
3. **재사용 모듈**: `pptx_sb/sb_helpers.py` — 이 스킬 패키지에 함께 포함돼 있어 **별도 설치가 필요 없다**. v1.6 하우스 스타일(파란 헤더 배지, 요약 박스, 번호 지시선, 컬럼 스펙 그리드, 인터랙션 상태 그리드, 표지, 버전 관리 표)이 전부 함수로 있다. 이 SKILL.md를 읽은 실제 경로 기준으로 같은 폴더의 `pptx_sb/sb_helpers.py` 를 찾는다 (설치 위치는 사람마다 다르므로 **사용자에게 경로를 묻지 않는다**). **작업을 시작할 때 이 모듈을 `projects/{프로젝트}/sb_helpers.py` 로 복사한 뒤 그 사본을 import 한다** — 스킬 폴더의 원본을 직접 참조하지 않는다. 플러그인은 계속 갱신되므로, 과거에 승인된 SB 를 다시 빌드했을 때 결과가 달라지면 안 되기 때문이다. 플러그인을 제거해도 기존 빌드 스크립트가 살아있다. 이미 사본이 있으면 덮어쓰지 말고 그대로 쓴다. 사본이든 원본이든 **모듈 자체는 수정하지 말고** import 해서 콘텐츠만 채운다.
4. **파이썬 의존성**: `python-pptx`, `Pillow`가 사용자 환경에 없으면 설치를 안내한다(`pip install python-pptx Pillow`).
5. **Windows + PowerPoint** — 렌더 검증(PNG 내보내기)과 안전한 파일 닫기(`close_if_open`)가 PowerPoint COM 자동화로 동작한다. 없으면 이 두 기능만 빠지고 PPTX 생성 자체는 가능하다.
6. 원 요구사항 문서(있으면) — SB 완성 후 반드시 원본 요구사항과 항목 단위로 대조한다. 부가 아이디어·수정 요청이 쌓여도 원본 요구사항 커버리지가 항상 최우선 기준이며, 업그레이드는 되어도 누락은 안 된다.
7. **작업 위치는 반드시 사용자 프로젝트 폴더 아래 `sb_build/`**(예: `projects/{프로젝트명}/sb_build/`) — 세션 임시 폴더에 만들면 세션 종료 시 사라져서 다음에 그 프로젝트 SB를 못 고친다. 폴더 구성 권장안:
   - `node_map.json` — 슬라이드별로 필요한 Figma `fileKey`/`nodeId` 매핑 (아래 1단계 결과물)
   - `build_sb.py` — sb_helpers를 import해서 실제 PPTX를 조립하는 빌드 스크립트
   - `assets/` — `get_screenshot`/`download_assets`로 받은 원본 PNG
8. **버전 관리 페이지는 모든 SB에 고정으로 넣는다** — 표지 바로 다음 슬라이드로 `sb_helpers.build_version_slide`를 쓴다. 새로 만드는 SB든 기존 SB를 갱신하는 것이든 예외 없이 넣는다.

## 실행 순서

### 0. SB 만들기 전: 확인 질문 · 목업 점검
- **사용자가 정할 수 있는 건 SB 만들기 전에 묻는다.** 확인할 항목을 (1) 동작 정책(저장 방식 · 판정 기준 · 노출 조건 · 문구 · 꺼짐/켜짐 상태 등, 기술 용어가 섞여도 "어떻게 동작해야 하나"면 정책)과 (2) 데이터 · 시스템 사실(필드가 있는지, 연동이 되는지, 현행 값이 뭔지)로 가른다. (1)은 AskUserQuestion으로 먼저 받아 반영하고, (2)만 다른 팀 확인으로 남긴다. 다른 팀 확인으로 넘긴 뒤 "그냥 나한테 물어보지"가 나오면 실패다.
- **영역마다 정상 1케이스가 아니라 끝 경우까지 목업에서 띄워 본다.** 없을 때(0건: 영역 숨김인지, 빈 상자 · 빈 줄이 남지 않는지) · 적을 때(1~2건: 칸이 비어 보이지 않는지, 넘김 · 더 보기가 안 나오는지) · 너무 많을 때(최대 개수, 넘치면 「외 N」 · 더 보기, 고정 영역이 화면 밖으로 밀리지 않는지) · 긴 텍스트(상품명 · 업체명 등 말줄임, 마우스를 올리면 전체). 목업에 그 상태를 보여주는 케이스가 없으면 케이스를 만든다. SB에는 각 경우의 규칙을 한 줄씩 적는다.
- **현행에 이미 있는 동작 · 디자인은 새로 만들지 않고 현행 것을 쓴다.** 담기 후 반응(현행 담기 팝업), 호버 스타일(현행 상품 카드처럼 글자색), 카드 모양, 확인창 등. 목업에 현행에 없는 반응(토스트, 담긴 뒤 버튼 색 변화 등)이 들어가 있으면 SB 전에 걷어낸다. 새 인터랙션을 넣을 땐 현행 사이트의 같은 종류 요소가 어떻게 하는지 먼저 본다.

### 1. Figma에서 구조·좌표 확보 (`get_metadata`)
- 주어진 URL에서 `fileKey`/`nodeId`를 추출한다 (`https://figma.com/design/:fileKey/:fileName?node-id=1-2` → fileKey=`:fileKey`, nodeId=`1:2`). URL에 `node-id`가 없으면 프레임을 특정할 수 없으니 사용자에게 노드 지정 URL을 요청한다.
- `get_metadata(fileKey, nodeId)`로 해당 프레임의 자식 노드 구조(이름·타입·x/y/width/height)를 XML로 확인한다 — 컬럼 헤더 등 하위 노드의 좌표가 `build_column_slide`의 `boxes_px_rel`(번호별 픽셀 박스) 원본이 된다.
- **주의**: 여기 나오는 x/y는 캔버스 절대좌표다. `boxes_px_rel`은 캡처한 프레임 원점 기준 상대좌표가 필요하므로, 자식 노드 좌표에서 부모 프레임의 x/y를 빼서 변환한다.

### 2. 섹션/카드 스크린샷 확보 (`get_screenshot`)
- 컬럼 스펙 슬라이드용으로 섹션/카드 프레임 전체를 `get_screenshot(fileKey, nodeId, maxDimension)`으로 캡처한다.
- 기본 `maxDimension`(1024)은 표처럼 텍스트가 빽빽한 노드에는 흐릿할 수 있다 — 필요하면 2000~4000으로 올린다.
- **주의**: `sb_helpers`의 `crop_w`/`crop_h`(스케일 계산 기준)는 반드시 응답 메타데이터의 실제 렌더 `width`/`height`를 써야 한다 — 노드의 원본 캔버스 크기(`original_width`/`original_height`)를 대신 넣으면 `maxDimension`으로 축소된 이미지와 좌표계가 어긋나 번호 배지 위치가 틀어진다.
- 커넥터 등 겹치는 플로팅 요소를 빼고 싶으면 `contentsOnly: true`를 준다.

### 3. 인터랙션 상태 확보
- Playwright처럼 hover/click을 실행해서 만들어낼 수 없다 — 디자이너가 이미 만들어둔 상태별 프레임/variant 각각을 `get_screenshot`으로 캡처한다.
- 필요한 상태 프레임이 파일에 없으면 **상태를 추측·합성하지 말고** 컨펌 단계로 돌아가 상태별 프레임을 요청한다.
- 상태 안에만 있고 별도 텍스트로 안 뽑히는 문구(툴팁·토스트·안내문 등)는 `get_design_context`로 텍스트 레이어 원문을 확인해 해당 항목 설명에 그대로 인용한다.

### 4. 빌드 스크립트 작성
```python
import sys
from pathlib import Path
HERE = Path(__file__).parent
# [프로젝트 전용 사본] sb_helpers 는 이 프로젝트 폴더 안에 있다.
#   고쳐도 다른 프로젝트 SB 에는 영향이 없다 (프로젝트마다 사본을 둔다).
sys.path.insert(0, str(HERE.parent))
from sb_helpers import *

prs = new_presentation()

build_cover_slide(prs, "제목 — 화면설계 스토리보드", "Ver 1.0 / YYYY-MM-DD / ...", [
    "버전 관리",
    "SB-01  개요 — ...",
    "SB-02  ... — 컬럼 명세",
    ...
])

build_version_slide(prs, [
    ("v1.0", "YYYY-MM-DD", "최초 작성 — SB-01 개요, SB-02 ..."),
    # 기존 SB를 갱신하는 경우 기존 이력 행을 그대로 두고 새 버전 행을 이어서 추가한다 (덮어쓰지 않는다)
])

slide1 = new_slide(prs)
add_header(slide1, "SB-01", "...", "신규 개발")
add_summary(slide1, [[...좌측 불릿...], [...우측 불릿...]], height=2.6, size=9.5)
# 필요하면 add_rect/add_oval_badge로 캡처한 스크린샷 위에 번호 지시선 직접 그리기

build_column_slide(prs, "SB-02", "품절관리", img_path, crop_w, crop_h, boxes_px_rel, items,
                    legend_labels=["어드민 화면명: URL", ...])

# 표가 아닌 일반 화면 영역: 왼쪽 캡처 + 번호 박스, 오른쪽 번호 설명 (항목이 많으면 below=True 로 캡처 아래까지 이어 씀)
build_screen_slide(prs, "SB-0N", "재주문 체크 · 목록", "신규 개발", ["요약 한 줄"], img_path, crop_w, crop_h,
                   boxes_px_rel, [(1, "영역 제목", ["「다시 주문하실 때인가요?」"]), ...], img_w=18, below=True)

build_states_slide(prs, "SB-0N", "(1/M)", [[item1, item2], [item3], [item4, item5]],
                    state_dir=STATE_DIR, img_max_h=4.4)

# 분기가 있는 동작(업로드·저장 검증·결제·승인 등)은 글만 쓰지 말고 플로우차트 슬라이드로
build_flow_slide(prs, "SB-0N", "... · 업로드 동작", [
    {"text": "업로드 저장 클릭", "kind": "start"},
    {"text": "파일 선택됨?", "kind": "decision", "down": "예",
     "side": {"text": "알럿 ① · 중단", "label": "아니오"}},
    {"text": "확인창 ②", "kind": "process", "down": "확인",
     "side": {"text": "취소 · 변경 없음", "label": "취소", "tone": "neutral"}},
    {"text": "실패 행 있음?", "kind": "decision", "down": "아니오",
     "side": {"text": "전체 취소 · 알럿 ③", "label": "예"}},
    {"text": "저장 · 알럿 ④", "kind": "end"},
], [
    (1, "파일 미선택", ["알럿 「업로드할 파일을 선택해 주세요.」"]),
    ...  # 번호는 그림 안 ①~과 맞추고, 문구 원문은 여기에만 「」로
])

prs.save(OUT_PATH)
```
- `items` 튜플은 `(번호, 제목, 설명, is_check)` — `is_check`는 `False`로 둔다(확인 필요 항목은 아래 규칙대로 MD 체크리스트로).
- **확인 필요 항목은 SB 본문에 ★로 남기지 않는다.** 다른 팀(개발 · 데이터 등)이 답해야 하는 사실 확인은 기획 문서(MD) 맨 아래 「확인 필요」 체크리스트에 담당 팀별로 모은다(`- [ ] 내용 (SB-06)`). SB에는 확정된 내용만 적고, `is_check`는 기본 `False`로 둔다. 회신이 오면 SB 설명에 확정 내용을 채우고 체크리스트에서 지운다.
- **현행 기능은 「현행 ○○ 그대로」 한 마디로 끝낸다.** 현행 로직 · 현행 팝업 문구 · 현행 카드 구성을 풀어 쓰면 새로 바꾸는 요건처럼 읽힌다. 조건을 자세히 적는 건 새로 만드는 로직뿐이다.
- **화면 범위를 요약 박스 첫 줄에 적는다.** 기존 화면에 영역만 더하는 경우 「AI 영역은 ○ · ○ · ○ N곳. 나머지는 현행 그대로」처럼 손대는 곳과 안 대는 곳을 같이 적는다.
- **엠대시(—) 금지.** 제목 · 표지 · 설명 모두 가운뎃점(·) · 쉼표 · 괄호로 구분한다.
- 값이 원본을 그대로 보여주는 컬럼과, 산식으로 계산되어 나오는 컬럼을 구분한다 — 계산되는 컬럼(예: 비율·합산값)은 Figma 디자인 자체에 정보 아이콘·툴팁이 있으면 그 산식을 그대로, 없으면 원 요구사항 문서에서 확인한 산식(조건문 포함)을 SB 설명에 적을 것.
- 인터랙션 상태는 한 슬라이드에 2~3행(각 1~2칸)까지가 안전하다. 넘치면 빌드 중 「상태 슬라이드 넘침」 경고가 나온다. 항목이 넘치면 부록으로 빼지 말고 슬라이드 자체를 (N/총장수)로 나눌 것.
- 상태 슬라이드(캡처 + 설명 칸)는 모든 장에서 같은 배치: **왼쪽 캡처 · 오른쪽 번호 · 제목 · 설명**. 화면 구성 슬라이드(캡처 왼쪽 · 영역 목록 오른쪽)와 같은 방향이라 한 기획서 안에서 통일된다. 가로로 긴 캡처(목록 행 · 배너 등)는 한 행에 한 칸씩, 한 행에 칸은 2개까지(`build_state_row`가 이 배치로 그림). 공통 인터랙션처럼 캡처 + 표가 섞인 장도 캡처 설명은 캡처 오른쪽에 두고 표는 그 아래에. 단, 화면 전체 폭을 쓰는 헤더 · 배너 캡처에 번호를 찍고 아래에 번호별 설명 칸을 나열하는 장은 위아래 배치 그대로.
- 조건에 따라 문구가 갈리는 항목(데이터 있음 / 없음별 제목 · 툴팁 · 배너 문구 등)은 「있을 때 「…」, 없을 때 「…」」로 줄줄이 쓰지 말고 설명 안에 상황별 표로 넣는다. 열은 「상황 · 구분 · 문구」(구분 = 제목 · 툴팁 등), 같은 상황 칸은 세로로 합치고, 문구 칸을 가장 넓게 둬서 한 문구가 한 줄에 들어가게 한다. 문구가 하나뿐인 「첫 줄 / 둘째 줄」 설명은 표로 만들지 않는다.
- 캡처에 보이는 요소는 빠짐없이 번호를 단다. 팝업 제목 · 닫기(×) · 카드 안 이미지처럼 「당연해 보이는」 요소도 번호 박스 + 설명을 붙이고, 요약 박스에만 한 줄로 적고 끝내지 않는다. 번호는 캡처를 읽는 순서(위 → 아래, 왼쪽 → 오른쪽)로 매긴다. 항목이 늘어 설명이 넘치면 설명을 2단으로 나누고, 단이 좁아 단어 중간에서 끊기면 문장을 짧게 끊거나 「」 문구를 어절 경계에서 직접 나눈다.
- 한 장 안의 번호는 모두 같은 파란 원 배지 + 제목 + 설명으로 표시한다. 같은 장에서 ①은 배지, ②③은 표 안의 글자처럼 섞으면 어느 게 몇 번인지 못 찾는다. 캡처가 없는 항목(브라우저 기본 알럿 · 확인 창 등)도 표 대신 배지 블록으로 쓰고, 번호는 장마다 ①부터 다시 시작한다((2/2)를 ④부터 잇지 않음). 다른 장에서 가리킬 때는 「SB-23 (1/2) ②」처럼 쪽까지 쓴다.
- SB 안에서 다른 장을 가리킬 때는 「(2/4)」처럼 쪽 번호만 쓰지 말고 「SB-06 (2/4)」처럼 SB 번호까지 쓴다.
- **분기가 있는 동작은 플로우차트를 함께 넣는다** — 업로드·저장 검증·결제·승인처럼 조건에 따라 결과가 갈리는 동작(갈림길 2개 이상)은 글로만 나열하지 말고 `build_flow_slide`로 왼쪽 플로우차트 + 오른쪽 번호 설명 슬라이드를 만든다. 글만 있으면 검사 순서(예: 양식 오류는 확인창 전에 막고, 행 실패는 저장 단계에서 걸림)가 안 보인다. 판단은 마름모, 중단·실패는 빨간 테두리, 정상 흐름은 파란 테두리. 그림 안에는 짧은 라벨과 번호(①~)만 넣고, 알럿·확인창 문구 원문과 실패 사유는 오른쪽 설명에만 「」로 적는다(같은 문구를 두 번 쓰지 않는다). 「실패 처리」처럼 결과를 뭉뚱그리지 말고, 실패로 보는 조건·사유 문구·화면 반응(알럿·취소 범위·실패 사유 파일 열)을 각각 적는다.
- 설명 문장은 한 줄에 한 문장씩 문단을 나눈다(「」 · 괄호 안의 마침표는 나누지 않음). 한 문장이 줄바꿈되면서 끝 몇 글자(「음.」 · 「하나만.」 · 「).」 등)만 다음 줄로 떨어지면, 그 문장을 둘로 나누거나 줄여서 없앤다. 제목 / 부제처럼 짝으로 적는 문구도 한 줄씩 따로 쓴다. 문장을 나누면 설명이 길어지므로, `build_states_slide` 처럼 설명 칸 높이가 고정된 슬라이드는 행 높이를 설명 길이에 맞춰 다시 계산하고(다음 행 침범 방지) 이미지 · 표를 설명 아래에 붙인 슬라이드는 위치를 다시 확인한다.
- 목업 검토용 정보는 SB에 쓰지 않는다: 가상 병원 · 테스트 계정 이름, 캡처에 쓴 케이스 · 검색어(「캡처: 가상 병원 7」, 「검색어 「린코」」 등). 개발자는 그걸로 만들 게 없다. 상태는 「도래 있는 회원」 · 「고정 품목을 담은 직후」처럼 조건으로만 적는다.
- 논의 중 빼기로 한 것을 「~는 표시하지 않음」 · 「(토스트 없음)」 · 「(넘김 없음)」처럼 부정형으로 남기지 않는다. 개발자는 결과만 보므로 있는 것만 적는다. 단, 조건에 따른 규칙(「5개 이하면 넘김 없음」)이나 동작 규칙(「체크는 바뀌지 않음」)은 결과라서 적는다.
- SB가 20장을 넘으면 `add_sections(prs, [("표지 · 개요", None), ("헤더", 2), ...])`로 PowerPoint 구역을 화면 단위로 나눈다(prs.save 직전). 구역 경계는 헤더 배지의 SB 번호로 판정.
- 크기 · 여백 · 글자 크기 같은 px 수치는 쓰지 않는다(목업에서 임의로 정한 값이라 디자이너가 정할 영역). 배치 관계와 동작만 적는다(예: 「검색창 오른쪽에 버튼 자리를 두기 위해 검색창 폭을 줄임」).
- 기획자끼리의 규칙(화면에 없는 내부 명칭 설명 등), 당연한 말(「담기는 고객이 누를 때만」), 캡처에 이미 보이는 배지 · 버튼 색을 「공통 규칙」으로 다시 모으지 않는다. 개요는 대상 화면 · 대상 회원 · 화면별 SB 번호만. 여러 영역이 같은 동작(담은 뒤 팝업 · 알럿 · 확인 창 등)을 쓰면 「공통 인터랙션」 장에 한 번만 정의하고 각 영역은 번호로 가리킨다. 시스템 알럿 · 확인 창은 캡처 없이 알럿창「문구」 · 버튼만 적는다.
- SB 텍스트에는 산출물 자체에 대화 흔적을 남기지 않는다 — 왜 이렇게 정했는지 논의 서사 없이 결론(판정 공식, 데이터 출처, 식별자 등)만 담백하게 적는다.
- 기존 SB를 수정하는 경우 버전 관리 표에 새 행(버전·일자·변경 내용)을 추가하고 파일명도 버전을 올린다(`_v1.0` → `_v1.1` 등) — 이전 행은 지우지 않는다.

### 5. 렌더 확인 (자체 검수 루프)
```python
from sb_helpers import close_if_open, render_slides_to_png
close_if_open(OUT_PATH)          # PowerPoint에서 열려있으면 안전하게 닫기
# ... prs.save(OUT_PATH) 재실행 ...
pngs = render_slides_to_png(OUT_PATH, out_dir, slide_numbers=[1, 2, 3])
```
내보낸 PNG를 직접 열어 다음을 확인한다:
- 텍스트가 박스/이미지 밖으로 넘치지 않는지 (특히 불릿·설명 텍스트가 길어졌을 때)
- 캡처 글자가 읽히는지: 상태 슬라이드 한 칸에 세로로 긴 캡처(목록 전체 등)를 넣으면 작아져서 못 읽는다. 설명할 부분만 크롭하고(예: 펼친 묶음 하나), 그래도 작으면 슬라이드를 (1/2) · (2/2)로 나눠 긴 캡처끼리 한 장에 크게 둔다.
- 캡처와 설명 사이가 벌어지지 않는지: 캡처와 번호 · 제목은 같은 높이(칸 위쪽)에서 시작하고, 설명이 캡처보다 길면 행 높이가 설명에 맞춰 늘어난다. 납작한 캡처 옆 설명에서 「요」.」처럼 끝 글자만 떨어지면 `img_frac`을 줄여 설명 칸을 넓히거나 문장을 「」 경계에서 직접 줄바꿈한다. 전체 화면 슬라이드의 영역 목록은 슬라이드 오른쪽 끝이 아니라 캡처 바로 오른쪽에
- 배지 번호가 인접 도형에 가려지지 않는지, 반대로 배지가 작은 태그 · 글자를 덮지 않는지(덮으면 박스를 넓혀 배지를 요소 바깥으로) (Figma 캔버스 좌표 변환이 틀리면 여기서 어긋난 게 드러난다)
- 표지 TOC가 실제 슬라이드 구성과 일치하는지

겹침/오버플로 발견 시 텍스트를 줄이거나 박스 높이·이미지 위치를 조정하고 2~4단계부터 반복.

### 6. 원 요구사항 대조 + 정량 검증
- 원본 요구사항 문서가 있으면 항목별로 전부 커버됐는지 대조한다. 빠진 게 있으면 왜 빠졌는지(스코프 제외 확정인지, 그냥 누락인지) 확인 후 반영하거나 "이번 스코프 제외"로 명시적으로 처리한다.
- SB에 적은 산식·조건문을 원본 문서와 한 번 더 대조해서 AND/OR, 경계값(이상/초과), 예외 케이스(0으로 나누기 등)를 놓치지 않았는지 확인한다.
